一、研究背景与动机

过去两年，业界优化推理成本的注意力几乎全部集中在模型本身：量化、剪枝、投机解码、KV 缓存……但一个被忽视的事实是——数据"进入"模型的路径上，还躺着三笔隐性开销。

1.1 分词：缓存命中了，前端却没命中

LLM 服务系统普遍缓存 prompt 的 KV 状态，但绝大多数前端每次调用仍会对完整请求文本重新分词。这在编码智能体场景尤为致命：智能体每执行完一个工具调用，就要把累积的长对话记录重新提交一次。TokTier 团队统计了来自两个智能体生态的 153,951 次调用：中位调用仅追加约 1.4K 字符，只有 1.0%-3.6% 的调用会重建百万字符级的会话。更反直觉的是，在舰队级 prompt 缓存命中率高达 94.1% 的情况下，分词居然能占到首 token 延迟的 64%——KV 缓存把"计算"省了，分词却把"时间"重新花掉了。而复用之所以难，是因为哪怕只追加一小段文本，也可能改变前一段序列末尾的 token 边界，导致"从头重来"。

1.2 视觉 token：代码截图里的"空白税"和"无关税"

把源代码渲染成图片喂给多模态大模型（MLLM），是降低输入成本的一条热门路线。但单纯调整分辨率只解决了"清晰度 vs token 数"的取舍，却漏掉了两个更隐蔽的低效源：其一，换行、缩进产生的空白区域白白占用 token；其二，与当前指令无关的代码区域（比如你问"这个函数是干什么的"，截图里却躺着 200 行 import 和配置）同样被全量编码。更麻烦的是，最优压缩配置随输入、任务、模型而变，任何固定压缩比策略都注定顾此失彼。

1.3 向量检索：平均召回率掩盖的"方差黑洞"

RAG 是当前大模型应用的事实标准底座，而向量检索（ANN）的搜索参数（如 probe 数量、候选集大小）通常全局固定。问题在于：不同查询的"难度"天差地别——简单查询轻轻松松就能召回，困难查询则需要深挖很久。固定参数要么让简单查询浪费算力，要么让困难查询召回不足；而业界惯用的"平均召回率"指标，恰恰把这种逐查询方差掩盖掉了。QASP 的作者直言：这种方差才是真实线上体验的痛点。

💡 一个共同的诊断结论
三篇论文指向同一个病灶：输入侧的优化仍在沿用"全局固定策略"的旧思维——固定全量分词、固定压缩比、固定搜索参数。而真实负载是高度异构的：追加 1.4K 字符的智能体调用、与问题无关的代码截图、难度悬殊的检索查询。固定策略与异构负载之间的错配，就是"输入税"的来源。

二、核心方法

2.1 TokTier：把分词做成"有状态的服务"

TokTier 的核心契约只有一条：输出的 token ID 必须与对完整请求文本做参考分词的结果完全一致——不做任何近似，不改变模型看到的任何内容。在这个契约下，它分两条路径处理：

  1. 会话续写（有可复用前缀）：只对追加点附近的一个小窗口重新分词，通过"稳定边界检查"（stable-boundary check）确认拼接安全后再 splice 进旧序列；检查失败则扩大窗口重试，最坏情况回退到全量分词。关键洞察是：虽然追加文本理论上可能影响任意靠前的 token 边界，但在 GPT 系正则预分词规则下，边界变化只会发生在追加点附近，可以高效验证
  2. 无前缀的调用：把 GPT 家族的正则预分词拆解为"run-local"规则，直接在 GPU 上执行精确的预分词 + BPE，绕开 CPU 上的串行瓶颈

此外，TokTier 部署了一个采样影子验证器（shadow verifier）持续复检线上流量，确保"状态化"永远不会悄悄退化成"有状态但错了"。

2.2 CodeShrink：三重手段压缩"代码截图"

CodeShrink 由三个组件构成，分别对应三笔不同的浪费：

  • 空白消除渲染（Blank-Free Rendering）：不再依赖空白符布局，而是用紧凑布局 + 显式结构标记（如行号、缩进符号）重排代码图像，从源头消灭布局诱导的 token——这是对"渲染方式"动刀，而非对"渲染结果"动刀
  • 自适应压缩配置（Adaptive Compression Configuration）：用一个强化学习训练的轻量代理，为每个输入预测"token 效率 vs 可读性"的最优平衡点。这一步承认了"最优配置因输入、任务、模型而异"的现实，把压缩从固定比策略升级为逐输入决策
  • 主导 token 选择（Dominant Token Selection）：推理阶段联合分析指令与代码图像，剪掉与当前任务无关的视觉 token——相当于给"代码截图"做了一次查询条件化的注意力聚焦

三者叠加的效果是：压缩不再是"无脑缩放"，而是"渲染层去布局税、决策层按需配置、推理层按指令剪枝"的三级过滤。

2.3 QASP：一次回归预测"整条召回曲线"

QASP 的出发点是一个优雅的抽象：与其为每个召回率目标训练一个预测器、或者在搜索过程中反复调用模型，不如在搜索前用一次监督回归，预测该查询完整的"召回率-代价"曲线——有了这条曲线，任何召回率目标都能直接推导出对应的搜索策略（如 probe 数量）。

为了保证泛化性，QASP 使用尺度不变特征（scale-invariant features）做预搜索推理，因此可以跨召回率目标、跨索引配置、跨数据集使用，无需重新训练。更妙的是，细粒度的进度预测还催生了一个轻量反应式补丁：搜索过程中把"预测进度"与"实际观察进度"对比，一旦偏离就动态调整搜索深度——而且不需要额外推理开销。理论上，作者证明了 QASP 只需要一个与数据集规模和维度无关的有限训练样本，其损失与任何固定策略的不可约下界只差一个可消失的余项，且相对固定 probe 策略的数据访问节省随内在维度呈指数增长。

四、技术启示与发展方向

💡 启示一：系统栈的"最后一公里"正在成为新的性能富矿
TokTier 揭示了一个残酷的事实：当 KV 缓存把推理计算压到极致后，前端的分词反而成了最大的延迟单项。缓存优化是"存量红利"，而分词这类"被遗忘的环节"才是下一块洼地——类似的"最后一公里"（序列化、调度、前后处理）大概率还有不少。
💡 启示二：输入表征的"布局税"值得被认真对待
CodeShrink 提醒我们：多模态输入的 token 成本不只是"内容"决定的，呈现方式（layout）同样决定 token 数。换行缩进都能产生可观的空白 token——这意味着输入侧的优化不只是"压缩算法"问题，还是"渲染设计"问题，后者甚至更便宜、更有效。
💡 启示三："平均指标"正在系统性误导系统设计
QASP 的批评具有普适性：平均召回率掩盖逐查询方差，平均延迟掩盖长尾。按需自适应（per-query / per-input 决策）正在取代全局固定策略——这条规律在分词窗口、压缩配置、检索深度三个完全不同的环节同时出现，绝非偶然。

4.1 三篇论文的共同信号

  • 精确性保证：TokTier 以"零分歧"为生命线，CodeShrink 与 QASP 都以"不损失精度/召回"为前提
  • 轻量代理：RL 训练的压缩代理、单次回归的曲线预测器——决策者都很小，不喧宾夺主
  • 按需自适应：稳定边界检查、逐输入压缩配置、逐查询搜索策略——固定策略全面退场

未来方向：把这三层优化叠进同一条链路——QASP 先按查询难度决定检索深度，TokTier 保证长对话追加的毫秒级重分词，CodeShrink 在视觉输入进入模型前完成指令感知剪枝。当"检索、分词、编码"都变成按需自适应，"输入税"才有可能被真正系统性减免。

五、总结

三篇论文，三个环节，一个共识：当模型能力与推理计算都被优化到极致，输入侧的低效就成了最后的"隐形税"。

TokTier 告诉我们：缓存命中了，分词还在全量重来——状态化可以比"从头再来"快两个数量级；CodeShrink 告诉我们：视觉输入的浪费藏在布局与无关区域里——压缩应该是逐输入的决策而非固定比例；QASP 告诉我们：平均指标掩盖方差——一次回归预测整条曲线，检索就能按查询难度量入为出。

这或许是大模型基础设施走向成熟的一个标志：优化对象从"模型怎么算"延伸到"数据怎么进"。当输入侧的每一毫秒、每一个 token、每一次数据访问都被重新计算价值，AI 服务的成本结构才真正完成了从"蛮力时代"到"精算时代"的转身。
