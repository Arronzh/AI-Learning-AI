工具调用的"苦涩教训"：普华永道 14 模型实测，让模型"写代码"调用工具正在全面超越 JSON

📌 核心摘要：大模型调用外部工具，如今几乎清一色靠"输出一段 JSON"——每个函数调用都要模型吐出一个结构化 JSON 对象，一轮推理一次调用。但普华永道（PwC）商业技术创新办公室的研究者提出了一个尖锐的问题：对于一个本来就会写代码的模型，JSON 是必需品，还是只是历史惯性？ 他们把工具暴露为带类型的 Python 存根（stub），让模型直接写 Python 脚本来完成调用（程序化工具调用，PTC），并在 BFCL v4 基准的 309 条子集上对 14 个模型（覆盖 2024 年 11 月至 2026 年 7 月发布的 5 个 Anthropic 模型和 9 个 OpenAI 模型）做了系统对比。结果：11/14 模型在 PTC 下达到或超过 JSON 基线，GPT-5.6 家族平均提升 10.6 个百分点；链式调用场景下，链长 ≥12 时 PTC 领先 JSON 多达 18.8 个百分点；并行扇出场景下，JSON 在 Claude Sonnet 5 上存在硬性上限（N>70 枚举率开始崩溃，N=100 时归零），而 PTC 在 N=100 时仍保持 100% 枚举准确率；在 128 个 schema 的"上下文洪水"压力下，JSON 平均退化 2.3%，PTC 反而提升 5.5%。论文标题致敬 Rich Sutton 的经典文章——工具调用，正在迎来它的"苦涩教训"时刻。

一、研究背景与动机

从 Sutton 的"苦涩教训"说起

2019 年，强化学习教父 Rich Sutton 写下那篇著名的《The Bitter Lesson》：依靠人类先验知识的特化方法，最终总是败给"通用方法 + 更多算力"——围棋如此，语音识别如此，计算机视觉亦如此。七年后，普华永道的研究者把这句话搬到了工具调用（Tool Calling）的战场上。

现在的 Agent 生态有一个近乎默认的"宪法"：模型调用工具，就是输出一个符合函数 schema 的 JSON 对象，通过 API 的 tools 参数传给服务端。Anthropic 的官方 Agent 教程、各大云厂商的函数调用接口、生产环境里的记忆系统 Chronos……全是这套 JSON 循环。但研究者提醒：对于已经能写可执行代码的模型，JSON 只是一个设计选择，而不是必然。

代码动作的"理论承诺"与实证缺口

"用代码代替 JSON"并非新想法。2024 年的 CodeAct 已经证明：在多工具任务上，代码动作的任务成功率最高提升 20%，交互轮次减少 30%，增益集中在并行和组合式场景。Cloudflare 的 Agents 平台甚至已经把代码执行作为原生的工具使用接口（目前仍是实验特性）。

但此前的证据存在一个共同缺口：没有人在标准基准上、跨多个模型家族、跨多代模型，系统比较过"代码调用"与"JSON 调用"。更关键的是，函数调用与普通的 coding-agent 任务不同——它要求精确的参数序列化、多步链式调用、跨异构 API 的扇出（fan-out），这些恰恰是"范式选择"影响最大的地方。普华永道的这篇论文，就是来补这个缺口的。

二、核心方法

两种范式，同一个评分标准

研究者选取了 BFCL v4 基准的 309 条代表性子集，覆盖 8 个任务类别，用确定性评分器（直接对比 stub 输出与 ground truth）评估——这一步很聪明，因为最近一项审计发现 BFCL v4 的 LLM-judge 模式存在 20% 的评估者-人类不一致，确定性评分绕开了这个坑。

两种范式唯一的区别在于"如何表达和执行工具调用"：

- JSON 工具调用（基线）：系统提示词中放入 JSON 格式的函数定义，模型每调用一次函数就输出一个结构化 JSON 对象，一轮推理对应一次调用；

- 程序化工具调用（PTC）：把基准里的函数 schema 编译成带类型的 Python 存根模块，模型写一个 Python 脚本 import 这个模块并调用函数；agent loop 在 shell 子进程里执行脚本，从 stdout 提取函数名和参数值。脚本执行后不再有额外的推理轮次——一次推理 + 一次子进程执行，搞定所有调用。

三个消融实验：专打 JSON 的"软肋"

研究团队设计了三个消融，直指 JSON 范式最常被诟病的场景：

1. 链式调用（Chaining）：n=52，链长 2–20。JSON 范式下每跳需要一次推理轮次（调用 f1 → 拿到返回值 → 再推理调用 f2）；PTC 则把整条链写进一个脚本，中间值靠参数化知识直接传递；

2. 并行扇出（Parallelism）：n=32，扇出数 7–48。考验"一次响应里枚举 N 个并行调用"的能力；

3. 上下文腐烂（Context Rot）：n=31×2，对比"只给相关 schema"（filtered）与"128 个 schema 洪水"（flood，混入无关领域的干扰 schema）。

全部实验在 temperature=0 下进行，准确率定义为"每条目所有必需调用都出现且参数正确"的比例。14 个模型覆盖 20 个月的发布周期：Claude Haiku 4.5 → Sonnet 5，GPT-4o → GPT-5.6-Terra。

三、实验结果

1. 主评测：11/14 达标，胜负按"代际"划分

BFCL v4 主评测的结果呈现出一个清晰规律：PTC 是否可行，取决于模型代际，而不是模型家族。

- Anthropic 全线达标：5 个模型（Haiku 4.5 到 Sonnet 5）全部达到或超过 JSON 基线，增量 0.0 到 6.5 个百分点；

- GPT-5.6 家族全面正增益：GPT-5.6-Sol 从 72.2% 涨到 82.8%（+10.6%），GPT-5.6-Terra 从 73.5% 涨到 84.1%（+10.6%），GPT-5.6-Luna 76.1% → 80.3%；

- 三个老模型集体崩溃：GPT-4o（81.9% → 55.0%）、GPT-4.1（81.9% → 62.1%）、GPT-5.4-mini（79.3% → 55.0%），绝对跌幅 19.7%–26.9%。

失败模式高度一致且非常"工程化"：这三个模型在多行脚本里输出的是字面的 `\n` 转义序列，而不是真实换行符，导致任何超过单行的脚本在子进程里直接语法错误。耐人寻味的是，更小更早的 GPT-5-nano 反而没有这个问题——说明这个 bug 的修复是在 GPT-5.4-mini 与 GPT-5 之间的某次训练数据更新里完成的。同一个系统提示词、同样的换行指令，不同模型行为迥异，排除了提示词配置的原因。

2. 链式调用：优势随链长放大，长链拉开 18.8 个百分点

链式消融中，PTC 的优势随链长增长而放大：链长 ≥12 时，PTC 对 JSON 的绝对领先达到 18.8 个百分点，而短链上几乎无差异。原因很直接——JSON 范式每跳多一次推理轮次，链越长，累积的轮次开销和错误传播越致命。

单模型亮点：Claude Sonnet 5 从 80.8% 跳到 96.2%，Claude Opus 4.8 从 80.8% 跳到 94.2%。唯一的反向离群值是 GPT-4.1：98.1% → 40.4%，还是那个 `\n` bug——链式任务中每一步中间计算都需要多行脚本，所以它在这里摔得最惨。

3. 并行扇出：JSON 撞上"结构性天花板"

并行消融中，PTC 在 13/14 模型上达到或超过基线。最大赢家是 GPT-5：71.9% → 96.9%——它的 JSON 基线在扇出数超过 13 后就开始退化，而 PTC 在所有扇出水平上保持接近完美的枚举率。

研究者还专门探测了 Claude Sonnet 5 的扇出极限：JSON 枚举率在 N≤70 时 100%，N=72 时跌到 75%，N=100 时归零；而 PTC 在 N=72 和 N=100 都保持 100%。不过这个"硬限制"并非 JSON 的普适属性——GPT-5.6-Sol 的 JSON 基线到 N=100 依然 100%，说明这是 Anthropic 模型序列化并行调用块的方式导致的特定结构限制。

Token 成本也在 N≈26 处交叉：低于此阈值 PTC 因固定系统提示词开销更贵；高于此阈值 JSON 反超——N=48 时 JSON 要 5,097 token，PTC 只要 3,535。

一个值得警惕的细节：论文把枚举准确率（是否真的发起了全部 N 个调用）与聚合准确率（最终汇总答案对不对）分开报告。因为不少模型会直接用参数化世界知识"猜"出正确的聚合答案（比如直接说出人口前三的国家），根本没执行工具——这按评分器标准算对，但测不出工具使用的真实性。枚举率才是范式保真度的主指标。

4. 上下文腐烂：洪水之下，JSON 退化、PTC 逆势上涨

在 128 个 schema 的洪水条件下：JSON 平均退化 2.3%，PTC 平均提升 5.5%，而作为内部参照的"文件系统发现式"方法暴跌 32%。PTC 对无关上下文干扰的鲁棒性，来自它的机制本身——脚本只 import 需要的存根，多余的 schema 根本不进入执行路径。

5. 延迟：链式任务耗时减半

PTC 在 13/14 个模型上把链式任务的墙钟时间压到基线的一半左右（耗时比 0.32–0.96）。唯一的例外是 GPT-5——2.8 倍基线延迟，因为它超长的推理输出把省下来的轮次红利全吃掉了。

四、技术启示与发展方向

第一，"苦涩教训"正在 Agent 领域重演。 代码是通用、可扩展、可组合的基质：循环天然表达扇出、脚本天然表达链式、子进程天然隔离执行；JSON schema 则是特化的、带硬上限的格式。Sutton 的判断在工具调用上再次应验——通用方法最终胜出。Cloudflare 把代码执行作为原生工具接口，正是这一趋势的注脚。

第二，范式选择本质上是模型选择。 PTC 的可行性高度依赖模型的代码生成能力，胜负按代际划分而非家族划分。对部署者的直接启示：如果你在用新一代模型（GPT-5.6、Claude 4.5+），PTC 是值得认真评估的默认选项；如果你还在跑 GPT-4o 级别的老模型，先修代码生成能力再谈范式迁移。这也意味着"工具调用能力"正在与"代码生成能力"合流——未来模型的工具调用训练，很可能就是代码训练的一部分。

第三，格式脆弱性是真实的工程风险。 那个 `\n` 转义 bug 提醒我们：同样的提示词在不同代际模型上的行为可能天差地别，基准测试若只测"新模型"，会系统性高估范式的普适性。跨代际、跨家族的评测矩阵，应该成为工具调用评估的标配。

论文的局限也很诚实：BFCL v4 用的是 echo-return 存根（函数原样返回参数，不执行真实 API），所以测的是参数序列化准确率而非端到端工具使用正确性——真实返回值影响下游调用时，结论未必完全迁移；消融样本量偏小（每条件 n=31–52），单模型结果应视为方向性信号，只有 11/14 这类跨模型聚合模式才可靠；PTC 还有固定输入 token 开销（链式场景 1.5×，高扇出时反转）。

未来方向：真实 API 返回值下的端到端评测、更长链与更复杂依赖图的压力测试、以及"代码生成训练与工具调用训练融合"的模型侧探索。

五、总结

一句话概括这篇论文：工具调用正在经历它的"苦涩教训"时刻——让模型写代码，正在取代让模型写 JSON，但这道选择题的答案写在模型的代际上。 对新一代模型，程序化工具调用是更准、更快、更抗干扰的选项；对老一代模型，它是一面照出代码生成能力短板的镜子。

当 Agent 越来越依赖工具去"行动"时，接口的选择不再只是工程细节，而是决定系统能力上限的架构决策。普华永道这篇论文的价值，在于用 14 个模型、20 个月的代际跨度，把这场范式之争从口号变成了数据。JSON 不会立刻消失，但"写代码调工具"的时代，已经来了。
