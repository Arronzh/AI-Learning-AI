为什么 CLAUDE.md 永远写不完？"灾难性记住"揭示 Agent 提示词的无限膨胀，SkillZip 用"最短忠实解释"给技能瘦身

📌 核心摘要：如果你用过 Claude Code、Cursor 或任何 agentic 编程工具，大概率见过这样一个文件：CLAUDE.md、AGENTS.md 或 copilot-instructions.md——它记录了让 AI 助手遵循的规则，然后越写越长，几乎从不删减。今天精选的两篇 arXiv 论文，从两个角度解剖了这个"知识膨胀"问题。第一篇（arXiv:2608.11095）把这种病命名为"灾难性记住"（catastrophic remembering）——它是"灾难性遗忘"的镜像：在 1,867 个仓库、247,694 条指令生命周期的观测中，agentic 提示词平均膨胀 +226%，每次提交净增 4.9 条指令，而且指令越老越不可能被删除；根因是"写下时很便宜、删掉时很昂贵"的不完美记忆——记录一条指令的理由只花 O(1)，事后重建它却要 O(2^|D|)。解法朴素得惊人：给提示词写注释，把"为什么写这条指令"编码进去，即可消除 99.3% 的多余指令。第二篇（arXiv:2608.11079）来自阿里+浙大+杜克，聚焦自我进化 Agent 的技能库：技能随进化轮次膨胀到初始的 5.2 倍，而 SkillZip 用"最短忠实解释"目标（类型化最小描述长度 + 硬覆盖约束）在零 rollout、零评估的条件下压缩技能 31.2%，性能不降反升，速度比评估驱动的 SkillReducer 快 3.5 倍。一个说"记不住是病"，一个说"忘不掉也是病"——两篇论文指向同一个判断：Agent 的知识资产正在失控膨胀，而解药是结构化的"为什么"，不是更多的"写什么"。

一、研究背景与动机

先看提示词这一侧：一个每天都在发生的"事故"。 任何用过大模型编程工具的人都有体会：为了让助手别再犯某个错，你在配置文件里加一行；为了让输出格式稳定，再加一行；为了处理某个边角 case，又加一行。每一行单独看都合理，但文件整体在不可逆地生长。CLAUDE.md 论文的作者（Kushal Chakrabarti，独立作者）用一个尖锐的类比开场："如果英语是新的代码，为什么我们还没有注释？" 软件工程几十年前就解决了"代码为什么这样写"的问题——用注释。但 agentic 提示词文件里，指令只有"做什么"，从没有"为什么"。

为什么只增不减？作者给出了信息论式的解释。 追加一条指令的成本是 O(1)——把失败经验写下来就行；但删除一条指令的成本是 O(2^|D|)：你必须确认在剩下的 |D| 条指令构成的组合空间里，删掉它不会让任何一条约束失效。当写下指令时的"潜在推理"（当时为什么加它、它防的是什么错）随时间衰减后，删除的唯一安全选项就是整文件推倒重写。于是出现了一个反直觉的动力学：即使任务完全不变，提示词也会无限增长——因为"记忆为什么"在衰减，而"记得什么"只增不减。作者把这命名为"灾难性记住"，与持续学习领域研究了三十年的"灾难性遗忘"互为镜像：遗忘是"该保留的没留住"，记住是"该覆盖的没覆盖"。

再看技能这一侧：自我进化 Agent 的"笔记本困境"。 SkillZip 观察的是另一类知识资产——自我进化 Agent 的技能库。这类 Agent 把成功的流程、失败的修复不断追加成可复用技能（SkillProx、SkillOpt 等进化框架就是干这个的）。问题在于：文本增长与程序化增长系统性脱节。"永远不要覆盖源文件"可能同时出现在开头、三个工作流分支和一个示例里；同一段"校验-修复-验证"序列被复制了无数次，只有细微差异。每次更新局部合理，累积起来却是灾难：技能注入越来越贵（上下文成本），维护越来越难。

两条线的共同困境：评估驱动的压缩为什么不够？ 面对膨胀，直觉是"用任务跑一遍，看哪些内容没用就删"。但两篇论文都指出了这条路的结构性缺陷。CLAUDE.md 侧：删除需要反事实验证（删了会不会回归？），维护者根本无法穷举。SkillZip 侧：评估驱动压缩（如 SkillReducer）需要 rollout、算力，而且把压缩结果绑定在压缩时的评估集上——一个稀有分支可能在任何采样任务里都没被激活，但它恰恰是关键；反复在有限样本上调优还会引入自适应的选择效应。SkillZip 于是提出一个更严格的问题：能不能只利用技能里已经存在的结构，不观察任何任务、奖励、轨迹或验证器，就把技能缩短？

二、核心方法

2.1 CLAUDE.md：把"为什么"写进注释，让最小覆盖可观测

论文的第一半是诊断：把 agentic 提示词拆成单条指令，在 commit 历史上追踪每条指令的"生命周期"。语料规模惊人——1,867 个 GitHub 仓库、1,801 个多版本文件、299,440 次版本间变迁、247,694 条指令生命周期。三个关键发现：

  • 棘轮效应：64.3% 的仓库指令数净增长（只有 26.6% 净减少），中位数净增 +7 条；每次提交平均净增 +4.9 条；文件在其生命周期内平均膨胀 +226%（指令数）和 +140%（总字节）。中位文件最后携带 39 条指令（90 分位 131 条）——早已越过"指令跟随性能随约束堆积而下降"的阈值。
  • 删除是"清仓"而非"修剪"：76.8% 的指令"死亡"发生在一次整文件重写里。重写后文件掉到重写前的 59.5%，但 10 次提交内就恢复到 91.5%——而且重写后增长更快（每次提交 +4.9% vs 重写前 +4.1%）。棘轮并没有被重置，只是被短暂清零。
  • 根因判定：不完美记忆。删除风险随指令年龄下降（log-hazard 斜率 -0.032/commit，95% CI 排除 0）——这直接否定了"指令过时"假说（过时会预测风险随年龄上升）；gamma frailty 模型排除"脆弱指令早死"的成分效应后斜率仍在（-0.0355）。最决定性的是：删除风险还随维护者人数衰减（β = -0.021，z = -11.7）——只有"记忆衰减"假说能预测这个交互项：人越多，每条指令的"为什么"越分散、越难找回。

论文的第二半是疗法：给提示词加注释。方法上最精巧的贡献是 Inverse-IFEval——把 IFEval 基准"倒过来"用：把每条基准项的指令藏起来当作"已知最优的最小覆盖 D*"，保留验证器作为世界的隐藏约束集，再让一个更强的模型把指令"有损概括"成一句模糊的任务目标（如"起草一份产品公告"）。于是研究者获得了一个最优解已知的"可验证世界"：维护者只能看到被审查的噪声反馈来重建指令集，实验组被允许给每条指令写一条携带"潜在推理"的注释（这条指令防的是什么失败、假设是什么、效果如何），执行器永远只看指令、看不到注释。指令告诉执行器做什么，注释告诉下一个维护者为什么——这个分工被强制执行。

2.2 SkillZip：把技能当作"带类型的契约"，求最短忠实解释

SkillZip 的核心观察是：技能不是一段扁平文本，而是一份"紧凑操作手册"。它有接口（名称、用途、触发器、排除项）、过程（步骤、分支、循环、回退）、工具与输出的契约、以及作用域可全局可局部的规则。这种结构暴露了 token 重要性看不见的冗余：

  • 每条分支里重复的规则 → 可以在分支前只声明一次（作用域提升）；
  • 反复复制粘贴的动作序列 → 命名一次、处处引用（工作流复用）；
  • 多个带守卫的变体 → 写成一条通用规则 + 显式例外；
  • 而稀有但唯一的规则——即使只被激活一次——必须保留（硬覆盖约束）。

作者把这套直觉形式化为一个类型化最小描述长度（MDL）目标：最小化"紧凑技能契约的成本 + 契约未能解释的源细节成本"，同时要求每个抽取出的触发器、工作流边、工具要求、义务和输出字段都被硬覆盖。这等价于"把三份复制的代码片段替换成一个函数加三次调用"——为共享结构付一次钱，只为真正的差异单独付钱。

工程上提供两种模式：One-shot（一次结构化抽取调用 + 确定性优化，压缩一个已进化的技能快照）和 Zip-on-Write（持续模式：每个新进化补丁只与当前紧凑契约的兼容部分比较，要么吸收、要么细化既有规则、要么新增要求、要么触发局部重构；周期性重打包捕捉多次更新后才显现的复用模式）。全程零任务、零 rollout、零验证器——压缩器只做两件事：受 schema 约束的契约抽取，和确定性的最小覆盖求解。

三、实验结果

CLAUDE.md：注释消除 99.3% 的多余指令，性能持平

在 Inverse-IFEval 的 552 条维护历史上（15 步和 51 步两档），结果近乎理想：

实验组（T=51）最终指令数超额大小约束满足率（t=T）
对照组（无注释）6.6+211.3%44.0%
安慰剂（注释形噪声）5.3+147.9%42.6%
治疗组（信息注释）2.2+1.4%44.0%

信息注释把超额大小从 +211.3% 压到 +1.4%（消除 99.3%），而约束满足率与对照组完全持平——提示词几乎收敛到理论最优的最小覆盖（|D*| = 2.2）。T=15 档同样干净：+60.4% → −5.8%（66.2pp 的改善）。消融实验揭示了注释的"有效成分"：注释必须携带结果（发生了什么、效果如何）——注释形噪声与无注释组无异（+53.2% vs +60.4%），而"只有尝试过程、没有结果"的叙事竟是最差组（+70.0%），因为它把未经验证的前提传给继任者；单是去掉"复发次数"字段就损失 37% 的收益。更有意思的是规模效应：维护者越强（3 个能力档位），无注释组的超额从 +67.7% 飙到 +571.9%——更强的模型反而更会"棘轮"，而注释在最强档位带来帕累托改进。

真实场景验证（Inverse-WildIFEval，64 个世界、K=1 真指令 + G=16 条噪声指令）：噪声指令让真实指令的满足率从 65.6% 掉到 41.5%（损失 24.1pp）；而带注释的维护者在 3 轮内把满足率从 50.4% 抬到 62.0%（+11.6pp，相对提升 23.1%），且效应在第二个盲审裁判下复现。

SkillZip：零评估压缩 31.2%，性能不降反升

实验设置：3 个骨干模型（Qwen3.7-Max、Qwen3.6-Plus、Kimi K2.6）× 3 个基准（BFCL-v4 Web Search、LiveMathematicianBench、SpreadsheetBench），先用人写技能种子经 SkillOpt 进化 5 轮得到"膨胀技能"，再压缩。

RQ1 膨胀有多严重？ 技能长度随进化轮次单调增长：第 5 轮时分别膨胀到初始的 5.6× / 3.1× / 6.7×，平均 5.2×。重复规则、重叠工作流、越来越具体的例外不断堆积，每次调用都要为这份臃肿付上下文成本。

RQ2 压缩能保住保真度吗？ 能，而且略超。SkillZip 压缩率 27.1%–36.9%（平均 31.2%），宏观平均分 0.577 略高于未压缩进化技能的 0.570，9 个设置中 5 个持平或反超。对比基线 SkillReducer（评估驱动、结构感知重写）：压缩率 31.2% vs 9.2%，任务分 0.577 vs 0.544——双赢。原因在于两种方法针对不同冗余：SkillReducer 擅长清理公开技能里的背景废话；而自我进化技能是"知识密集型"的，冗余藏在重复约束、重叠作用域和复制的工作流里，结构性整合（而不是内容过滤）才是对症下药。

RQ3 成本？ 压缩耗时从 SkillReducer 的 587–1331 秒降到 SkillZip 的 207–332 秒，平均 3.5× 提速；SkillReducer 每次压缩要 40–80 次验证 rollout，SkillZip 全程 0 rollout——环境交互才是评估驱动方法的主要成本来源。

RQ4 跨模型泛化？ LiveMath 上跨源-目标模型的保留率 0.97（SkillReducer 0.91）——显式保留规则、守卫和输出约束，产出的是更与模型无关的技能表示。

RQ5 持续模式（Zip-on-Write）？ 16 轮进化循环里，无压缩时技能膨胀到 2.5×–3.7×；从第 1 轮就开启 Zip-on-Write 则全程封顶在 1.6×–1.9×（相对无压缩终点减少 38%–50%），且最终测试精度持平或略超——压缩没有用准确性换紧凑。但激活时机很关键：第 8 轮才开启只能部分挽回（Kimi 上 2.6× vs 1.9×）——冗余的预防比清除便宜得多。

四、技术启示与发展方向

1. "写什么"与"为什么"必须分离，这是 Agent 时代的软件工程第一课。 两篇论文给出一条共同的结构性处方：知识资产要区分"执行视图"和"维护视图"。CLAUDE.md 用注释隔离"做什么/为什么"（执行器只看前者）；SkillZip 用契约+残差隔离"共享结构/个别差异"。这恰好是软件工程里"代码/注释"分工的翻版——只不过这次被治理的对象是提示词和技能。对每一个维护 AGENTS.md、MEMORY.md 或技能库的人来说，这都是立即可用的实践：给每条规则附上"这条防的是什么错、何时加的、是否仍有效"，删除就不再是赌博。

2. 删除的数学决定了 Agent 记忆管理的边界。 O(2^|D|) 的反事实成本解释了为什么"只增不减"是所有 Agent 记忆系统的默认态——也解释了为什么整文件重写（清仓）成为唯一可行的删除方式。这提示我们：记忆系统的设计目标不该是"更好的删除"，而是"更好的可恢复性"——让"为什么"在写入时就被结构化保存（注释、来源、时间戳、关联的失败案例），把删除成本从指数级拉回常数级。这与 8/10 精读的 SkillProx（技能审计与删除）形成呼应：SkillProx 用留一法效用审计做删除决策，而这两篇论文回答了"为什么需要审计、审计缺什么"。

3. 评估驱动 vs 结构驱动的压缩，是两种互补的范式。 SkillZip 证明了"只看结构、不看行为"的压缩不仅能保住性能，还避免了评估集过拟合和 rollout 成本；但论文也坦诚其边界——它针对的是"知识密集型"的进化技能，对含大量背景叙述的公开技能，SkillReducer 式的去肥仍然必要。未来方向明确：把评估驱动的校验（行为侧）与结构驱动的压缩（文本侧）组合成流水线，前一轮去肥、后一轮整合。

4. 更强的模型 ≠ 更好的记忆维护者，反而更糟。 CLAUDE.md 论文最反直觉的发现：维护者能力越强，无注释提示词膨胀得越狠（+67.7% → +571.9%）。这与"能力越强越会推理"的直觉相悖，但机制上说得通——更强的维护者更善于把失败转成新指令（追加更快），而追加从不触发删除。这给所有"用强模型自动维护提示词"的方案敲了警钟：自动维护器必须显式携带"为什么"通道，否则它就是一台更快的棘轮。

五、总结

CLAUDE.md 论文告诉我们：Agent 的提示词是"灾难性记住"的重灾区——写下 O(1)、删掉 O(2^|D|) 的不对称，让指令只增不减、越老越稳，直到整文件被清仓重来；根因不是指令过时、也不是内容脆弱，而是"为什么"在衰减。解药朴素得近乎复古：把潜在推理写进注释，让指令告诉执行器做什么、注释告诉下一个维护者为什么——于是提示词收敛到最优覆盖，多余指令消除 99.3%，真实场景的指令跟随提升 23.1%。SkillZip 论文则给出技能侧的镜像答案：自我进化 Agent 的技能膨胀到 5.2 倍，而"最短忠实解释"原则（类型化 MDL + 硬覆盖）可以在零评估下压缩 31.2%、性能不降反升，持续模式把膨胀封顶在 1.9 倍以内。 一个在"记忆"侧重建了为什么，一个在"技能"侧重建了结构。两篇论文合起来是一份 Agent 知识资产管理的宣言："记不住"和"忘不掉"是同一种病的两面，解药都是把结构性的"为什么"在写入时保存下来——如果英语是新的代码，是时候给它配上注释了。
