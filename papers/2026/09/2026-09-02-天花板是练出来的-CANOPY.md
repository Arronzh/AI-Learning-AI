# 天花板是练出来的：CANOPY 用"多探索、少漂移"把 Qwen3-14B 纯 RL 送上 AppWorld 榜首

📌 **核心摘要**：小模型做长程 Agent 任务，"纯结果奖励 RL 很快见顶"几乎是学界共识——于是大家纷纷绕开 RL：加稠密奖励、上 SFT 冷启动、建技能库、请闭源大模型当脚手架。阿里巴巴研究团队（AlibabaResearch，arXiv:2609.01245）却认为这个"天花板"是**训练方式造出来的假象**，并把病因拆成两个：**信号饥饿**（组相对 RL 只有组内成败混合才有梯度，小组采样让最难的任务长期"失声"）与**策略漂移**（小任务池反复更新让采样分布坍缩）。他们给出的对策简单到近乎朴素——CANOPY（Coverage-ANchored On-PolicY RL）：**探索多一步，漂移少一步**。仅靠环境交互、无任何任务级监督与外部脚手架的 Qwen3-14B，在 AppWorld 长程交互编码基准上登顶公开榜（2026 年 2 月，Test-Normal TGC **86.9**、Test-Challenge **67.6**），比最强开源训练基线 ESAT 高近 12 分；同一套原则让 Qwen3.5-9B 在 SWE-bench Verified 上提升 **16.6 分**。全部训练栈将在 GitHub（SignalCoverageRL）开源。

## 一、研究背景与动机

想象一个在真实软件环境里工作的 Agent：它要写代码、执行、看报错、再修改，来回几十轮，最终只凭一组"期末考"（状态级单元测试）判定成败。强化学习天然适合这种"只看结果"的后训练，但圈内流传着一句话：**结果奖励 RL 在小型开源模型上很快就会撞上能力天花板**。于是围绕 AppWorld 这个基准，几乎所有工作都在做同一件事——绕过 RL：

- LOOP 发现最难的任务"有害"，直接把它们从训练池里丢掉；
- SAGE、AgentEvolver、SALT、GVPO 引入步骤级奖励、轨迹图信用分配、技能库等"更细的学分制"；
- ProST、CuES 用前沿模型轨迹做 SFT 或合成任务；
- 更极端的路线干脆放弃训练，用 Sonnet、GPT-4.1 这类闭源大模型加编排、技能检索、测试时调试（HCL-GP 报出 98.2 的超高数字，但用的是 Sonnet 4.6 + 联合场景协议 + 测试时调试）。

还有论文论证 RL 会**收窄**而非扩展基座模型的能力边界（RL 的 pass@1 打不过基座的 pass@k 重采样）。每个补偿方案都带着一个"读起来像天花板"的发现。

CANOPY 作者的态度很直接：**这个天花板是假的，是训练轨迹分布被扭曲的产物**。他们把扭曲拆成两个机制——信号饥饿与策略漂移——并逐一拆解。论文标题本身就是处方：Explore More（多探索），Drift Less（少漂移）。

## 二、核心方法

### 信号饥饿：梯度只出现在"有输有赢"的组里

GRPO 这类组相对优化没有评论家网络，而是对同一任务的 n 条 rollout 做组内标准化得到优势。问题在于：**当组内全是成功或全是失败时，优势全为零，这条任务在这一步不产生任何梯度**。若单条 rollout 成功率是 p，一个组"有信号"（成败混合）的概率是：

P_sig(p, n) = 1 − p^n − (1 − p)^n

对难任务（p=0.05）来说，组大小 n=8（此前工作的常见配置）时覆盖率只有 34%——**大多数时候梯度静默**；而 n=32 时升到 81%。更糟的是，组里偶尔出现的那条成功会被标准化放大成 √(n−1) 的高方差尖峰，一条幸运轨迹主导整组梯度。论文断言：此前 LOOP、GVPO 测到的"难任务有害"，其实是**探索不足的补偿性误判**，不是数据本身的性质。

处方"探索多一步"有三味药，全部是老成分：(1) **组大小由数据定，不靠拍脑袋**——用基座模型做一轮 pilot 估出最难档位的成功率 p̂_min，按 n ≳ ln(1−τ)/ln(1−p̂_min) 定组大小，CANOPY 取 n=32；(2) **最难的任务一个都不扔**——容易任务饱和后，它们恰恰是最后的梯度来源；(3) **每轮生成不设上限**——只截断环境返回，不截断模型自己的思考，让模型学会自主分配推理预算，长程纠错轨迹不再被一刀切。

为什么不干脆把奖励变稠密？部分学分奖励确实能在"全败组"里制造方差，但它是"替代品"：可能奖励了方向错误的局部进展。探索到位后，替代的理由就不存在了（消融里稠密奖励收益最小，见下）。

### 策略漂移：小任务池反复榨取的四重走样

交互环境只能提供有限的可验证任务（AppWorld 训练池仅 90 条），训练必然反复回访。论文把漂移溯源到四个原因：(1) **无锚目标**让采样分布收窄——熵下降、探索死亡，恰好发生在饱和已让信息组稀缺的时候；(2) **rollout 跨更新复用**——半个 batch 拆两次更新，第二次更新吃的是旧政策采的数据；(3) **按序列长度归一化的损失**——每条轨迹的贡献被自身长度稀释，长程纠错轨迹被系统性降权；(4) **稠密/替代奖励自带误差**。

处方"漂移少一步"同样克制：用**稀疏二值奖励**（全对才给 1，没有代理可漂移）；**严格 on-policy**——梯度 mini-batch 就是整个 rollout batch，每批只更新一次，重要性比恒等于 1（日志可验证）；损失改成**只对动作 token 的 pooled token 均值**（掩码掉环境 token，分母跨 batch 池化，每条轨迹的每个动作 token 权重相等）；外加一个轻量 **KL 锚**（β=1e-4，k3 估计器）把采样分布拉回基座模型的广度。另有工程细节"故障隔离"：只有服务层自认的外生故障（被邻居 OOM 误杀等）才从组里剔除，Agent 自己触发的超时、死循环照常记零。

### 测试时预算转移

训练用 50 轮 / 32k 上下文的预算（长预算让 rollout 成本爆炸），推理时直接放大到 100 轮 / 61k——**不做搜索、不做多 rollout 投票**。收益恰好落在最难的任务与训练中从未见过的应用上。

## 三、实验结果

**登顶榜单。** 训练配置：Qwen3-14B + verl/SGLang 异步 rollout + Megatron 更新，组大小 32（每步 2,880 条轨迹）、90 步、LR 3e-6、温度 0.9。在 AppWorld（9 个应用、457 个 API、约 100 个模拟用户、735 个任务，由状态级单元测试判定）上，单个 checkpoint 以 mean@1 拿到 Test-Normal TGC **86.9** / SGC 80.4、Test-Challenge **67.6** / SGC 50.4，登顶 2026 年 2 月公开榜。对比最强开源训练基线：ESAT（同为 Qwen3-14B）75.2/58.5——**领先近 12 / 9 分**；LOOP、GVPO（Qwen2.5-32B）72.6/49.4 上下；SAGE 72.0/50.1；SALT 66.2。基座模型在同一预算下 m@4 仅 32.4，**训练净增超过 50 个 TGC 点**——买来能力的不是骨干网，是训练本身。

**"能力在权重里" vs "能力在脚手架里"。** 榜单上两个更高分都来自闭源前沿模型加外部机械：HCL-GP（Sonnet 4.6 + 联合场景协议 + 测试时调试）98.2、ASSAY（Sonnet 4.5 + 技能检索）89.3；而同一个 Sonnet 4.5 只做朴素 ReAct 是 83.9——机器要重建、能力不留权重。CANOPY 推理时只是一个 checkpoint 回答一个 prompt：**无编排、无技能库、无检索记忆、无测试时调试，且任何人可自托管**。论文还正面回应"RL 收窄能力边界"的说法：单次采样 86.9 超过基座 best@4 的 58.9 达 28 分（Test-Challenge 67.6 vs 37.7）——这个规模上，RL 加出了重采样够不到的能力。

**诊断与机制吻合。** 训练日志显示：全败组约 10 步内消失；训练奖励饱和到 0.99 后全胜组接管、信息组占比下降——正是公式预测的"高 p 端信号耗尽"；按难度分层，最难档位 L3 在 L1/L2 早已静默后仍是最后的梯度来源。KL 锚的消融最直观：约 70 步后无锚运行的熵坍缩到 0.038、Dev 卡在 81.6，有锚运行熵保持 0.217、Dev 继续升到 87.3，全程无需 early stopping。

**逐组件消融（各重训 90 步，改一个设置）：**

- 组大小 n=8（此前工作的规模）：**−16.4**——覆盖侧最贵的代价
- mini-batch 减半（一次 batch 分两次更新）：**−17.4**——漂移侧最贵的代价
- 去掉 KL 锚：−7.0；序列级损失替代 token 级：−5.4
- 丢掉最难档位：−6.0——**直接反转"难任务有害"的既有结论**
- 稠密奖励替代稀疏：−1.8——部分学分只是补偿，不是必需

**迁移到更硬的领域。** 在 SWE-bench Verified 上换 Qwen3.5-9B + 纯 bash 的 mini-swe-agent，训练数据来自 SWE-rebench 并按仓库级去污。结果 resolve rate 从基座 31.3 提到 **47.9**（mean@4，+16.6）、best@4 从 43.8 到 58.0（+14.2）；测试时放大预算再 +2.3。原则照搬、超参重调（组大小 16、KL 系数 1e-2、无补丁终态记 −0.2）——两个故障、同一套解法，在真实仓库修复里同样成立。

## 四、技术启示与发展方向

第一，**"难数据有害"的结论需要重审**。当组大小从 8 涨到 32，同一批最难任务从"毒药"变成"最后的药"——此前多个工作据此删数据、换奖励，很可能是在为探索不足买单。任何"某类数据有害"的结论，都应先问一句：是数据的问题，还是采样规模的问题？

第二，**脚手架叙事 vs 权重内化，是当前 Agent 路线的分岔口**。一边是把能力堆在闭源大模型外部的编排与检索（能力强、不可移植、每次换场景重建）；一边是把领域交互技能练进小型开源模型的权重（单 checkpoint、可托管、能力随权重走）。CANOPY 的证据是：后者的天花板比社区报告的高得多，至少在小模型+清晰领域这个象限里，"模型本身"仍是被低估的方向。

第三，**克制的工程值得尊敬**。CANOPY 没有改优化器、没有加任何辅助模块，六味药全是成熟成分（大组、稀疏奖励、on-policy、KL 锚、token 级损失、预算转移），论文却把每个成分的代价与理论排序一一对账——"简单"与"简陋"的区别，在于有没有诊断撑腰。

第四，**边界同样清晰**。训练池只有 90 个标准化任务，规模与多样性是最大短板；组大小按 pilot 点估计的启发式只是下限而非最优；14B 单模型在更重的前沿协议（如 HCL-GP 的联合场景）面前仍显单薄。作者自列的三个方向——环境规模化、更省样本的算法（按当前成功率 p 自适应组大小）、领域中期训练——也即：探索更多、漂移更少之后，下一步是让这套做法在更大世界里依然成立。

## 五、总结

CANOPY 的故事内核是一个方法论信念：**当一个方向被普遍认为"到头了"的时候，先别急着绕路，检查一下是不是路本身没走对**。结果奖励 RL 的"天花板"，被拆成了可诊断、可修复的两个工程故障——信号饥饿靠"多探索"治愈，策略漂移靠"少漂移"约束。86.9 的榜首 TGC、+50 的能力跃迁、+16.6 的跨域迁移，买主都是同一个东西：把探索预算花在刀刃上、把更新锚在基座上。当行业竞相给 Agent 搭越来越高的脚手架时，这篇论文提醒我们：**有些能力，本来可以长在模型自己身上**。
