# 「抽到的服务器，一半根本没启动」：一次不修复、不重试的随机抽样，称出了 MCP 生态与工具基准里被悄悄筛掉的那一半

📌 **核心摘要**：当研究者要测量 MCP（Model Context Protocol）服务器生态时，绝大多数已发布服务器根本跑不起来——于是文献普遍用参考集、热门榜、手工筛选，甚至"多智能体自动修复"来绕开这个问题。这篇由独立研究者 Haseeb Mohammed Afsar 完成的工作（arXiv:2609.10962），选择了"不绕开"：从 24,135 个服务器的登记册里做一次概率抽样，抽 400 个 npm/stdio 服务器，每个只探一次，**不修复、不给凭证、不重试**，并且为全部 400 个抽取对象都记录结果。结果只有 **48.8%** 完成了初始化握手，而手工筛选的参照帧在同一把尺子下是 **66.7%**；主导失败不是"缺凭证"（13.3%），而是"**根本启动不了**"（37.5%）。同一把尺子随后转向工具使用基准：BFCL v4 的 8,726 条原始记录里 **68.8%** 是"名称+描述"完全重复，UltraTool 英文集 **85.6%**，而真实 MCP 只有 **0.4%**；去重后，BFCL 的近重复有 **16.4 个点落在独立任务之间**，真实 MCP 跨作者的近重复则是 **0.0%**。一句话：不同的抽样会把同一个世界称出不同的重量，而这份工作把"筛选"这只看不见的手，称成了可以量化的 **17.9 个百分点**。

## 一、研究背景与动机

**规模已经有人测了，被抹掉的那个量没有。** MCP 让大模型应用通过统一的 JSON-RPC 2.0 接口发现并调用外部工具，围绕它已经出现了一批实证工作：登记册漂移测量、面向公网的安全评估、生态级运行时分析、仓库级克隆检测。这些研究确立了"规模"，但规模本身回答不了一个更窄、也更基础的问题。

**每个行为层面的 MCP 研究，都先得跨过同一道坎：** 绝大多数已发布的服务器根本无法直接启动、无法对话。文献给出的解法，本质上都是"选择"——

- **参考集与热门榜**：筛出"人们已经在用的服务器"；
- **手工筛选帧**：筛出"策展人能把它弄跑的服务器"；
- **修复管线**：MCPZoo 这个目前最大的运行时集合，用多智能体框架把服务器修到能跑，把收集到的 64,611 个服务器变成 37,288 个可做动态分析的服务器。

每一种都是合理的工程答案，但**它们都抹掉了同一个量：已发布种群中，究竟有多大比例是"到手即死"（dead on arrival）。**

**这篇论文的动机，正是把这个量测出来——方法就是"不去解决它"。** 作者从登记册抽取一个概率样本，对每个样本只探一次，不修复、不提供凭证，并为全部 400 个抽取对象都记录结果，无论"入选"还是"被排除"，连同原因一起存档。

**动机的第二层，是把同一把尺子转向外。** 既然已经拿到 2,766 条真实、独立作者、已部署服务器实际广告出来的工具描述，就可以反问：它们和工具使用基准呈现给模型的工具描述，差在哪里。已有的基准批评多针对"评测器"（例如评测器与人类的错配率、重复运行的分差），而本文问的是同一批产物里的另一个问题——**被评分的语料本身，长什么样。**

## 二、核心方法

**一条三阶段的测量管线。**

**① 普查层（Census）。** 一个采集器通过游标分页横扫整个官方 MCP 登记册，只记录自陈元数据：部署模型、包生态、声明的传输方式、生命周期状态、固定的 $schema 版本。这一层**不运行任何第三方代码**，因此可以扩展到整个已发布种群；它记录页数、版本行数与 sweepComplete 标志，被截断的运行会被标记为"下界"而不是静默上报。快照有两个：2026-07-14 与 2026-08-22，两次都是完整扫描。

**② 抽样与探测（Sampling & Probing）。** 抽样框是普查产出的"npm 发布、声明 stdio、活跃"服务器，在 2026-08-22 快照上有 7,258 个候选。作者用**已发布种子 20260819** 做无放回抽取 400 个：先按登记册标识规范化排序，再用种子化的 mulberry32 生成器做部分 Fisher–Yates。抽取清单记录了抽样框字节的 **SHA-256**，所以"针对移动后的框重抽"会被检测出来，而不是被默认等价。每个被抽到的包经 npx 以 stdio 启动，用 mcp-probe 探测一次：直接说 MCP 线协议、完成 initialize 握手、通过 tools/list 枚举工具、并按规范对每个工具的 JSON Schema 做校验。**始终不提供凭证、不调用任何有副作用的工具、不修复、不重试，每一个抽取对象都记录结果。**

**③ 冗余测量（Redundancy）。** 三个语料用**同一个方法衡量**。单位是"工具名 + 完整描述"，每个语料在计算相似度前先用这个精确键做**全局去重**——这一点在代码里强制，而不是靠自觉，因为早期一次迭代里的按文件去重键漏掉了跨文件重复，把某个测得的数字**抬高了 14 个点**。向量化用 TF-IDF（词 unigram + bigram、次线性词频），各自语料单独拟合、从不共享词表；相似度用余弦。阈值 t 处的冗余率定义为"至少有一个其他工具与其余弦 ≥ t 的去重工具占比"——作者特意写出定义，因为**换一种定义会得到另一个数字**。此外还单独报告每个原始发布的**完全重复率**，因为它是与近重复率不同的、后果更重的量。

**三个语料分别是：** 真实 MCP（195 个入选服务器广告的 2,766 个工具）、BFCL v4（8,726 条记录；注意 20 个发布文件中有 7 个根本不暴露 function list，包括四个多轮文件和 memory 文件）、UltraTool EN（14,084 条）。每个源文件都用 SHA-256 固定在发布出的溯源记录里。

## 三、实验结果

### RQ1：一次"不修复"的随机抽样，究竟抽到了什么？

400 次抽取的结果如下，**没有任何服务器被静默丢弃**：

| 结果 | 数量 | 占比 |
|------|------|------|
| 入选（完成握手） | 195 | 48.8% |
| 排除：握手失败 | 150 | 37.5% |
| 排除：需要凭证 | 53 | 13.3% |
| 排除：包不可用 | 2 | 0.5% |

两个结论随之而来。

第一，**随机抽样能用的部分，远少于手工筛选。** 同一把仪器跑在一个 24 个服务器的**手工筛选帧**（参考服务器 + 热门社区服务器）上，24 个里入选了 16 个，即 66.7%。这 **17.9 个百分点的差距，就是"筛选"所引入的选择效应的规模**——是测出来的，不是断言的。

第二，**主导失败模式并不是文献预期的那一种。** 人们通常用"缺凭证"解释"公开服务器为何探不了"，它占了 400 次中的 53 次；而"根本启动不了"占了 150 次，**接近前者的三倍**。换言之，在行为类 MCP 研究真正取样的那类抽样框上，大约**每五个已发布条目里有两个是"惰性"的**。这正是修复管线被造出来要消除的量——对它们自己的目的而言这是合理的工程选择，也正因如此，**它们的样本报不出这个数字**。

### RQ2：跑起来的服务器长什么样？

195 个入选服务器广告了 2,766 个工具（其中 2,759 个带描述）。每服务器工具数高度倾斜：最少 1，中位数 8，95 分位 46，最多 300；有一台入选服务器一个工具都没广告。

**硬性合规（Hard conformance）：** 2,766 个工具中，**零致命 JSON Schema 违规**；195 台服务器同样零违规——没有缺失 schema、没有非法类型、没有畸形 properties/required。这把此前手工帧上一个 200 工具的结果、**以约 14 倍的规模、在随机而非选择样本上复现**，说明它是结构性属性而非小样本假象。"MCP 工具 schema 经常畸形"的直觉，并不成立。

**安全标注（Safety annotations）：** 可选标注（readOnlyHint、destructiveHint、idempotentHint、openWorldHint）用来在调用前告诉智能体某个工具是否安全。194 台至少广告一个工具的服务器中，72 台给每个工具都标了、122 台一个都没标；2,766 个工具里，**1,626 个（58.8%）完全没有标注**。而手工帧给出的是 41.5%——**筛选又美化了 17.3 个点**，理由和它美化入选率一样：参考服务器爱标注，而手工帧里塞满了参考服务器。因此，较低的那个数（58.8%）不应被当作"生态速率"来引用。

服务器层面几乎**双模态**：本样本中 194/194 台都是"全标或全不标"，没有观察到部分标注的服务器。作者刻意不把它说成绝对命题——单次样本"观察到零个稀有类别"只支持上界而非否定：给定 0/194，部分标注流行率的单侧 95% 上界是 **1.53%**。此外，本研究早期一次未发布的运行在 n=214 时报告过 4 台部分标注的服务器，本次没有复现，作者**如实报告了这处分歧而不去解释它**。

**协议版本：** 195 台服务器协商出四个版本——2025-06-18 有 192 台，另有 2024-11-05、2025-03-26、2025-11-25 各一台。最后这个比客户端自陈的基线还新，说明已部署种群里的版本分布是**双向**跑偏，而不只是一条滞后的长尾。

### RQ3：基准语料 vs 真实部署的工具

**原始发布，大多就是重复：**

| 语料 | 原始记录 | 完全重复 | 占比 |
|------|---------|---------|------|
| 真实 MCP（195 台服务器） | 2,766 | 10 | 0.4% |
| BFCL v4 | 8,726 | 6,002 | 68.8% |
| UltraTool EN（dev+test） | 14,084 | 12,052 | 85.6% |

**任何在这些文件上不做全局去重就算出的统计量，测的都是"基准把同一任务重复了多少次"，而不是"它包含多少个工具"。**

**去重后的近重复，以及它落在哪里：**

| 语料（去重后 n） | 配对范围 | 0.70 | 0.80 | 0.85 | 0.90 |
|------|------|------|------|------|------|
| 真实 MCP（2,756） | 全部 | 2.8% | 1.1% | 0.5% | 0.0% |
| 真实 MCP | 跨服务器 | 0.0% | 0.0% | 0.0% | 0.0% |
| BFCL v4（2,724） | 全部 | 16.7% | 9.7% | 6.2% | 2.7% |
| BFCL v4 | 跨任务 | 16.4% | 9.6% | 6.2% | 2.7% |
| UltraTool EN（2,032） | 全部 | 0.3% | 0.0% | 0.0% | 0.0% |

**这个"分解"改变了结论。** 真实 MCP 的每一处近重复都落在**单台服务器内部**——那是一个项目自然会产出的 list_x / get_x / create_x 家族；**跨独立作者，近重复在所有阈值上都是 0.0%**。BFCL 的冗余恰恰相反：16.7 个点里有 **16.4 个落在独立呈现的任务之间**，而且是三个语料里唯一在余弦 0.90 处仍有近重复的。

所以正确的说法不是"BFCL 比真实工具大概脏六倍"，而是：**BFCL 在任务之间自我重复，真实 MCP 不跨作者重复**。而 UltraTool（0.3%）比真实部署的工具（2.8%）还干净——两个为同一目的造的合成语料给出了相反的答案，因此**不存在**关于"合成工具语料这一类"的结论，作者也明确不下这种结论。

### 生态背景

**两次普查快照给出坐标：** 登记册种群在 39 天内从 16,548 增至 24,135 个唯一服务器，约每天净增 195 个。

| 部署模型 | 2026-07-14 | 2026-08-22 | 变化 |
|------|------|------|------|
| 仅包（本地安装） | 8,340（50.4%） | 10,530（43.6%） | −6.8pp |
| 仅远程（托管 HTTP/SSE） | 7,057（42.6%） | 12,004（49.7%） | +7.1pp |
| 两者都有 | 852（5.1%） | 1,224（5.1%） | −0.1pp |
| 都未声明 | 299（1.8%） | 377（1.6%） | −0.2pp |

仅远程在这扇窗口里反超了仅包（+70.1% vs +26.3%）。对本文真正重要的后果是**方法学的**：npm/stdio 切片——本地行为仪器能触达的那部分——绝对量从 5,804 涨到 7,414，但作为种群的占比却从 **35.1% 跌到 30.7%**。一个只做 stdio 的仪器，覆盖的是生态里一个**正在缩小的少数派**——这个限制同样适用于本文自己的行为层。

### 效度威胁（作者自陈）

- **握手过滤器被直接检验：** 跨作者冗余 0.0% 若是因为探针系统性地丢弃了克隆，那它就只是在美化。作者用三路检验（npm 包描述、作者家族集中度、单个高产地作者 125 个工具最大跨服务器余弦 0.623）都没找到过滤选择克隆的证据，但也不排除"克隆会改写工具描述"这种本方法看不到的情况。
- **跨单位列未配平功效：** 去重后 BFCL 平均每任务行 1.8 个工具，而真实 MCP 每服务器 14.2 个，去掉同单位配对对 BFCL 扣得更少；真实 MCP 从 2.8% 塌到 0.0% 方向相反，不能用它解释。
- **大服务器：** 把真实 MCP 每服务器上限截到 10/25/50，阈值 0.70 处得 0.9%/2.2%/3.0%，包住了未截断的 2.8%，说明不是那两台 300、122 个工具的大服务器在拉高。
- **行为层范围：** 只覆盖 npm/stdio（占种群 30.7% 且在降），远程、PyPI、OCI 都不在框内；入选由"单次探测无重试"决定，因此 48.8% 是"最终能启动比例"的下界。
- **相似度是词法的：** TF-IDF 余弦量的是词面重叠而非语义等价，会把三个语料的速率都往下压。
- **普查：** 元数据自陈；两次快照只支持"差异"而非"趋势"。

## 四、技术启示与发展方向

**1. 把"选择效应"本身当成一个要报告的测量量。** 这篇论文最有价值之处，是把"筛选"从一个隐含的方法学背景噪声，变成了一个可以称重的数字（17.9 个百分点）。任何做生态级实证的工作，都应当显式报告"未修复样本"的存活率，而不是只报告"我修好之后能测的那部分"。

**2. 基准语料在统计前必须全局去重。** 68.8%（BFCL）与 85.6%（UltraTool）的完全重复率意味着：不去重就统计，得到的不是工具分布，而是框架的复用模式。而"完全重复率"必须与"去重后近重复率"一起读，因为复用同一工具构造大量行本身就会抬高前者。

**3. 报告"分解"，区分谁在重复谁。** 把冗余拆成"单位内"与"跨单位"之后，"BFCL 在任务间重复"与"真实项目在服务器内重复"是两种性质完全不同的现象——不加分解的单一速率会掩盖这种差异。

**4. 固定仪器 ≠ 固定覆盖率。** 当 npm/stdio 的生态占比从 35.1% 降到 30.7%，即便仪器一字未改，它衡量的世界也已经在缩小。方法学论文需要把"覆盖份额"的变化和"结果"的变化分开陈述。

沿着这个方向，值得追问的是：其他依赖"可运行样本"的生态测量（浏览器扩展、容器镜像、插件市场、智能体工具链）里，同样的"到手即死"比例有多大？以及，当修复管线把"死件"救活，"救活后的样本"与"真实种群的可用率"之间，隔着多远的一段距离。

## 五、总结

这是一篇"反其道而行"的测量论文。面对"大多数 MCP 服务器跑不起来"这个所有同行都绕过的问题，它选择不去绕过，而是把它当作被测量对象本身。于是我们第一次拿到了几个具体的数字：随机抽样 **48.8%** 的存活率、**37.5%** 的"根本没启动"、**58.8%** 的工具没有安全标注；也第一次看清了工具使用基准的语料质地——**68.8%** 的原始重复、**16.4 个点**落在独立任务之间的近重复。它最锋利的贡献不在某个数字，而在一个态度：**当你发现所有同行都在用同一种方式筛选样本，那么"不筛"本身就是一种值得发表的实验条件。**

在这个"测量诚实"的主题下，它把"你测的那个世界是真实的，还是被挑出来的"问到了最底层。前几天的文章里，我们在测模型的能力、记忆、删除与承诺（9/5–9/9），测那些本该替我们测别人的审计员（9/10）；今天这笔落到更下面一层：**连"你要测哪些样本"这件事，都可能是被别人替你挑过的。** 一句话：**在你评价一项测量之前，先问一句——它抽到的，究竟是一份概率样本，还是一份被修好的展览品。**
