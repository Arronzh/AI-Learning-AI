# 「别只问模型行不行，要问框架值不值」：把 Agent 脚手架拆开算账——预写任务计划 +7.17 个百分点，一个只读验证器不到一分钱，把误放行从 57% 压到 21%

📌 **核心摘要**：一个 Agent 把活儿干成了，功劳该记给谁——记给模型，还是记给围着它转的那圈"脚手架"（计划、工具编排、记忆、完成检查）？这篇论文（arXiv:2609.20474，香港中文大学 / 爱丁堡大学 / 港中大（深圳））做了本系列一直想问、却很少有人真做的事：**把脚手架拆成组件，一层一层对照着算账**，用的是 τ²-bench 的 Retail 与 Airline 环境、三组实验（共享 Retail 1,547 条轨迹 / 计划专项 Retail 1,227 条 / Airline 233 条）。两个主结果。第一，**"给一份任务专属的计划"本身确有价值，而且不是靠"多塞了字"**——作者把"预写计划"（Fixed）与"把领域策略词打乱、字数对齐"的对照文本（Sham）配对比较，265 个配对单元里，Fixed 把 oracle 验证的成功率抬高 **7.17 个百分点**（90% 区间 1.15–13.36），且**增益几乎全压在高复杂度任务上**（+13.01 个百分点 vs 低复杂度的 +2.11）。第二，**一个只读的"终检器"（terminal verifier）能拦掉 61% 的错误完成，代价是每回合不到一分钱**（新增推理成本 $0.0079），把 Retail 的**误放行率从 57.21% 压到 20.96%**——但它同时**误扣了 17% 的正确完成**。最该记住的是最后一句：**"计划更值钱还是验证器更值钱"没有标准答案，它取决于你给"误接受"标了多高的价**。低责任场景里计划胜出；高责任场景里，验证器拦住误放行的价值反超，而且**一个独立验证器只用约 1/12 的成本，就拿到了完整"计划+验证"栈几乎全部的防误放行收益**。

## 一、研究背景与动机

**大模型的 Agent 能力，从来不是模型一个人的成绩。** 它取信息、调工具、改环境状态，而真正决定成败的，是围在模型外面的一整套执行与控制结构——论文把它叫 **agent harness（脚手架）**：计划、修复、记忆、工具编排、完成检查。ReAct 把推理与行动交织，Reflexion 加反思反馈，都是"组织方式改变模型行为"的现成例子。

**问题是，评测把这两者捆在一起量。** WebArena、OSWorld、AgentBoard、τ-bench、HAL 都测的是"模型 + 脚手架"合起来能到哪；当一份成绩单显示某套方案涨了 5 个点，你没法知道这是模型的功劳、提示词的功劳、还是某个检查环节的功劳。作者把话点破：**要把成绩归因到某个组件，需要一个更"贴身"的对照**——多加的指导、多花的推理、额外的执行约束、多给的修复机会，全都可能改变成功率，必须逐项隔离。

**此前已有零散的路标，但缺一张完整的账。** Zhong 与 Zhu（2026）提过一条 **H0–H3 阶梯**：模型与任务固定，只让"支持程度"逐级变化；Kapoor 等人主张做**受成本约束**的 Agent 对比；"Verifier Tax"记录了工具调用、计划、策略中介三种架构在安全与成功之间的权衡；VIGIL 与 Advani（2026）把"世界状态是否真的完成"与"Agent 的收尾汇报是否属实"拆开；Cao 等人区分了"结果对、过程违规"的 corrupt success。这篇论文站在这条线上，把三件事分开量：**oracle 正确性（Z）、Agent 是否宣称完成（S）、以及系统是否接受这次完成（R）**，然后分别去问"计划信息"和"放行控制"各自值多少钱。

**它追问的是一个评测学的基本问题：** 当我们说"这个 Agent 行"，说的到底是模型行，还是它的脚手架行？如果说不清，那所有关于"换模型/换框架"的决策，都是在拿一个混在一起的分数下注。

## 二、核心方法

### 环境与实验：三块拼图

- **共享 Retail**：1,547 条轨迹，6 个模型、16 个任务、**7 种配置**——Minimal、Planner Fixed、Planner Sham、Evaluator-only、Orchestrator-only、Verifier-only、Full Fixed。
- **计划专项 Retail**：1,227 条轨迹，5 个模型、24 个任务、4 种计划条件，用来做计划的主对照。
- **Airline 试点**：233 条轨迹，5 个模型、6 个任务、4 种配置，用来检验结论能不能跨环境。

环境取自 **τ²-bench**（Barres 等，2026）——一个"双控制"的对话式 Agent 基准：用户与 Agent 都能改环境状态，最终成败由**终态数据库**判定，而不是看话说得漂不漂亮。

### 三个量，把"对不对"和"放不放行"拆开

这是全文的测量骨架。设 **Z=1** 表示基准奖励 ≥0.999（**oracle 真的做对了**）；**S=1** 表示回合终止于 `USER_STOP` 或 `AGENT_STOP`（**Agent 宣称"我做完了"**）；**R=1** 表示终检器**拒绝**这次结果。于是：

- **验证成功** `Y_VS = Z`（真的对才算数）；
- **误放行** `Y_FP = S·(1−R)·(1−Z)`（**说了完成、通过了检查、结果其实是错的**）；
- **接受度** `A = S·(1−R)`。

这套定义的价值在于：**"做对了"和"被放行"从此是两个可以分别报告的坐标**。一个系统可以把误放行压到很低，却同时误扣一堆正确的完成——只报 oracle 成功率，这个权衡就被藏起来了。

### 计划对照：Fixed vs Sham vs Self

主对照是 **Fixed（预写任务专属计划）** 对 **Sham（把领域策略词打乱、再对齐字数与输入包装的对照文本）**。这样做的用意，是**把"内容有用"从"上下文变多"里抠出来**——两者字数、包装一致，唯一的差别是那份指导是不是真的和任务相关。另外还放了 **Sham–Minimal 安慰剂对照**（检验打乱文本本身是否伤性能）和 **Self**（让模型自己生成计划）。

### 统计与价值框架

配对按"模型 × 任务 × 重复"对齐，用**按任务聚类的 bootstrap**（5,000 次重采样）出区间，模型级对比再做 Holm 校正。价值部分则引入一套"责任场景"：给 oracle 成功记 **+V**、给误放行记 **−L**（单位美元），V∈{1,5,20}、L∈{2,200}，算出每种配置相对 Minimal 的**增量净价值**与**盈亏平衡责任强度**——也就是"要怕到什么程度，验证器才比计划更划算"。

## 三、实验结果

### 结果一：计划信息真的值 7 个百分点，且只帮复杂的任务

265 个配对单元、4 个模型、23 个任务，**Fixed 相对 Sham 把验证成功率抬高 7.17 个百分点**（90% 区间 [1.15, 13.36]）。**Sham–Minimal 的点估计是 +1.89 个百分点**（区间跨零），说明"打乱的文本"没拖后腿，这份增益不是包装效应。

模型异质性很扎眼：**DeepSeek Flash +13.4、Qwen +13.3、Doubao +4.3 个百分点，而 Kimi 是 −1.5**。最能说明问题的一对是 Qwen 与 Kimi——**两者 Minimal 基线几乎相同（10.17% vs 11.59%），对计划的反应却相反**。按复杂度切分，高复杂度组 **+13.01 个百分点**，低复杂度组只有 **+2.11**；三个复杂性代理（子步骤数、依赖深度、工具种类数）切出了同一刀。留一模型检验的点估计全部为正（5.05–10.20 pp），但区间在去掉 DeepSeek 或 Qwen 后会跨零——**方向稳，强度依赖模型构成**。此外，**自生成计划（Self）的效果因模型而异**：Qwen 比 Sham 高 16.95 个百分点，其余模型相对 Fixed 多为负——"给计划"和"生成计划"是两回事。

### 结果二：一个只读终检器，61% 的错误被拦下，代价不到一分钱

在共享 Retail 里，**终检器拒绝了 137 个 oracle 错误回合中的 83 个（61%）**，同时**扣下了 92 个正确回合中的 16 个（17%）**。把拒绝标记关掉、其余保持不变，就能还原"检查前"的误完成率：**(48+83)/229 = 57.21%**；实际误放行率是 **48/229 = 20.96%**——**一次拒绝，抹掉 36.24 个百分点**。两个口径的差几乎都来自拒绝标记本身（37.34 pp 里 36.24 pp 归检查，只有 1.09 pp 归检查前的执行差异）。六个 Retail 模型的配对对比**全部为负**。代价呢？**每回合新增推理成本 $0.0079，不到一分钱**。Airline 试点里同样拦下 61% 的错误回合，但对正确回合的误扣更高（41% vs Retail 的 17%）。

### 结果三：7 种配置的账本

池化后，**Planner Fixed 拿下了最高的验证成功率 0.4810、最低的单位成功成本 Cost@Success 0.0280**；**Verifier-only 的误放行最低之一（0.2096），验证成功率 0.4017，平均成本 0.0164**；**Full Fixed 误放行最低（0.1831），但验证成功率掉到 0.3592、平均成本冲到 0.0739，是全场最贵**。请注意：这些是**非配对**的池化均值，样本覆盖不一，真正的比较要看下面的配对场景。

### 结果四：谁更值钱，取决于你多怕"误接受"

在高责任任务（动作名含 cancel/refund/modify 等）里做配对估值，**排序会随责任强度翻转**：

- **低责任（L=2）**：Fixed 相对 Minimal 的净价值最大（约 $1.97），验证器次之；
- **高责任（L=200）**：**Full Fixed 约 $99.20、Verifier-only 约 $97.31**，把 Fixed（约 $35.13）甩开。

关键在组件拆解：**Verifier-only 避免了 48.38 个百分点的误放行，增量成本只有 $0.0079**；**Full Fixed 避免了 49.82 个百分点——几乎一样多，但增量成本是它的 12 倍（$0.0947），且验证成功率变化是负的（ΔP=−0.0411）**。换句话说，**一个独立、只读的验证器，用极小成本拿到了完整"计划+验证"栈几乎全部的防误放行收益**。交叉点也给了：**Verifier-only 约在 L≈$3.4 追平 Fixed，Full Fixed 又在 L≈$70 反超 Verifier-only**。

## 四、技术启示与发展方向

**第一，脚手架要"组件级"地评测，不能整体打包。** 本文的 Fixed–Sham 对照是一个可复用的范式：**用字数与包装对齐的对照文本，把"内容有用"从"上下文增量"里剥离出来**。任何声称"加了某层支持就涨点"的 harness，都该先过这一关。

**第二，验证必须同时报"拦对了"和"扣错了"两个数。** 本文的终检器拦掉 61% 的错误，也扣掉 17% 的正确——**只看 oracle 成功率，会把"扣下正确完成"的代价完全藏掉**。作者的建议很直接：把 oracle 正确性、完成宣称、接受决策三者的**联合计数**，连同 token 与成本一起报出来。

**第三，要报"模型级"结论，别只报池化均值。** Kimi 与 Qwen 基线相近却反应相反，正是"池化会掩盖交互"的活样本；个体模型还能主导某个特定对比。**组件价值是"模型 × 任务"的函数，不是一个常数。**

**第四，把"误接受的代价"写进部署决策。** 论文的责任场景框架把一个隐性问题显式化：**计划的信息价值与验证器的放行价值，随 L 此消彼长**。做 Agent 产品时，先问"误接受一次要赔多少"，再决定钱花在"教它怎么做"还是"拦住它别乱说做了"。

**第五，也要看清它的边界。** 主样本按 Minimal 成功率与任务突变状态筛选，覆盖有缺口；Airline 只有 6 个任务；两个环境都是公开基准，**参评模型可能训练时见过这些题**；论文**没有独立时间戳的预注册**，且部分托管端点版本与请求设置缺失；成本口径**只算推理开销**，计划撰写、集成、维护、人工复核、以及"误扣正确完成"的机会成本都未计入。其能力探针里，规划前沿（PF）分半信度不错（0.968），但失效检测敏感度（FDS）可靠性存疑（0.761），工具协调复杂度（TCC）测量偏弱——**这些都提醒：别把一次实验的排序当成普适定律。**

**方向**很清晰：在更大、更均衡的样本上做**前瞻性**验证；把被拒绝的案例**追到修复、上报或放弃**，才能同时量出"拦下错误的收益"与"扣下正确的代价"；以及建立**部署级**的完整成本账。

## 五、总结

这一篇，把本系列一路追问的母题又拐了个弯。9/10 是"审计员开始编造"，9/14 是"秘密从基准里漏出来"，9/15 是"分数干净不等于证据在场"，9/16 是"榜单再也排不出名次"，9/17 是"动手前会不会去取证据"，9/18 是"共识是这样被吹大的"，9/19 是"伤害只是换了副面孔"。它们都在问同一件事：**这个数，能不能信？** 今天这一篇换了个问法——**就算这个数能信，它该记在谁头上？**

**得到的是一张拆开的账本：** 一份任务专属的预写计划，值 **7.17 个百分点**，且几乎全花在复杂任务上；一个只读的终检器，值 **36.24 个百分点的误放行减少**，代价是每回合**不到一分钱**——但它也悄悄扣掉了 **17% 的正确完成**。而当"误接受"被标上不同的价，**"计划更值钱"和"验证器更值钱"会互换位置**；唯一稳的结论是——**一个独立、便宜的验证器，用 1/12 的成本拿到了完整栈几乎全部的防误放行收益**。

**留一面镜子在这里：** 我们太习惯把 Agent 的每一次成功都记在模型头上，再把每一次失败也记在模型头上。**可这篇论文说，脚手架的价值不是一个固定的数，而是一个"你有多怕它说错"的函数。** 当"要不要花这层成本做检查"变成一道纯粹的算术题时，**真正该先回答的，也许不是"换个更强的模型能涨几个点"，而是——你愿意为一次"它说做完了、其实没做完"，赔多少钱？**
