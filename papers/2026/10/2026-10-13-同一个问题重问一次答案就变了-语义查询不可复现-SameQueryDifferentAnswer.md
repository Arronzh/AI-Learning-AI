# 「同一个问题，重问一次，答案就变了」：把温度设成 0，语义查询引擎照样不可复现——重跑三套基准，0.07%–10.2% 的判定行当场翻脸、个别任务冲到 24.0%；仅仅几个百分点的抽取值变动，就把约三分之二的答案整个换掉；LRO-Bench 那份写好的实现建议里，28 项测试有 16 项根本撑不过重跑，连「同一份权重换一套部署」都能让答案、方差、乃至「有没有答案」全部改写

📌 **核心摘要**：**语义查询引擎（semantic query engine）把一次 SQL 查询里的每一行，都交给一个大语言模型去逐行判断**——**一句「这条评论是不是正面」在查询里本没有定义，模型说它是，它才是**。**而今天几乎所有语义查询基准，都是在一小撮「temperature 0」的执行上比较各家引擎的**——**温度设成 0 意味着贪心解码，人们默认：同一个查询再跑一遍，会得到同一个答案**。**这篇论文（arXiv:2610.13823v1 [cs.DB]，2026-10-09 提交；作者 Oktie Hassanzadeh、Dharmashankar Subramanian，来自 IBM Research 约克敦高地）把这句话当成一个待核验的断言，直接上去重跑了一遍**。**它把三套公开基准（SemBench、LRO-Bench、UDA-Bench）原封不动地塞回它们各自的 harness，记下全部 121.9 万次模型调用，**并逐行记下了每一个算子的输出**——这是任何已发表基准都不曾留下的东西**。**结论很冷**：**在 temperature 0 下，五轮执行之间，0.07% 到 10.2% 的行会改变它经过算子后的输出**（**取决于模型；个别任务高达 24.0%**）；**SemBench 已发表的结果里，21% 的文本结果在重跑之间质量都变了**——**包括那些计划本身是确定性的引擎**；**更关键的是「放大」**：**抽取值只变了几个百分点，经过计划一放大，UDA-Bench 上约三分之二的答案就变了样**；**因为一条答案暴露的行数 n 越多，它被复现的概率就越接近 e 的负 n 次方**。**论文的口号因此很短**：**temperature 0 并不能让一次语义查询变得可复现**；**而唯一真正管用的补救，是把「这条答案是从哪些算子输出里长出来的」记下来**——**每个输出约 39 字节，很便宜**。

## 一、研究背景与动机

**先把这篇论文要审的那件事讲清楚：它审的不是「某一次模型答错了」，而是一个被整个语义查询领域默认接受的前提——「同一个查询，再跑一遍，会得到同一个答案」。**

**论文开门见山地摆出现状**：**语义算子（semantic operator）把关系型查询处理往前推了一步**——**当一个 filter（「这条评论明显是正面的」）、map、join、ranking、aggregation 的每一行、每一对行，都由一个 LLM 连同自然语言指令一起判断时，查询答案就不再是一个确定的性质，而变成了一个分布**。**在此基础上，一整套引擎**（LOTUS、Palimpzest、DocETL、Snowflake Cortex、UQE、Sema…）**开始提供语义筛选、映射、连接、排序、聚合**；**优化器会把语义算子放进执行计划、用代理模型和级联（cascade）去校准**；**引擎还会把语义输出存下来复用**。**于是，模型的输出，前面一路变成了「查询答案」，中间变成了「物化出来的列」，后面又变成了「优化器用来校准的标签」**——**「它们会不会重复，因此是一个关于『查询处理所产出的数据』的问题」。**

**论文随即点出那个被跳过的前提**：**上面所有这些用法，都把「一次语义查询的执行」当成了「系统的性质」**——**再跑一遍，答案一样**。**「这个假设看上去很安全，因为基准都在 temperature 0 下执行查询，而温度 0 让解码变成贪心」**。**但论文马上补上一刀**：**对 LLM 来说，temperature 0 下的输出本来就会在调用之间变化**。**原因不在提示，而在服务器内部**：**推理服务器会把并发请求动态地打进一个批（batch），而批的组成会改变浮点算子的归约顺序**——**也就是说，一个请求的 logits，竟然取决于「谁和它共享了同一个批」**；**降精度会放大这个效应**。**开源服务器的「确定性模式」是可选项、只在某些 GPU 上可用、还会吃掉可观的吞吐**；**而且输出会随 GPU 型号和数量而变**。**托管 API 干脆不提供这种保证**；**「我们本文中的一个部署，就在两轮 campaign 之间变过一次」。** **一句话：一个通用语义查询引擎，不能假设它的模型端点是确定性的。**

**接着，作者把空白精确地划了出来**：**「已知的是：temperature 0 下输出会变。未知的是：这对查询处理意味着什么。」** **论文把它们拆成四个很具体的问题**：**有多少输出会变？这些变化能不能穿过上面的算子活下来？它们会不会改变基准的结论？原因是什么？基准和引擎又能做什么？** **为了把这个「未知」钉成可测量的东西，论文给了一个极短的例子（Example 1.1）**：**SemBench 的 Movie Q3，要在 120 条候选里数出某部电影的正面评论数**。**在 gpt-oss-120B 上用 SemBench 自己的 LOTUS 计划和提示、在 temperature 0 下执行 10 次，它返回了 4 个不同的计数**，**而 SemBench 自己的质量指标在 0.64 到 0.93 之间摆动**。**同一个例子里还有更刺眼的一格**：**Llama-3.3-70B 在一套推理服务上，每次都返回同一个计数（质量 0.43）**；**在另一套服务相同权重的栈上，它也每次都返回同一个计数**——**但那是另一个数（质量 0.36）**。**「每一次都确定」和「两次确定地不同」，就这样被摆在了同一张图上。**

**对这个问题，前人分成三条互不相交的线**。**第一条线只谈「模型输出在 temperature 0 下会变」**（**代码生成、LLM benchmark 的研究都报过**，评测指南也在要求误差棒）；**第二条线谈「语义熵、自洽性」**——**用高温采样之间的分歧当信号**；**第三条线是数据库与群智计算的老传统**——**概率数据库、带噪声的人类判断、用冗余和投票来兜底**。**论文指出，这三条线都没有回答它要问的那件事**：**它们量的是自由文本输出或聚合准确率，而它要量的是「查询计划内部的算子输出」**——**在那里，关系算子会把许多个小的逐行判断，合成同一个答案**。**「一条答案依赖的行越多，它就越难被复现」——这层放大关系，正是被前面所有工作漏掉的那一环。**

**对本系列一路追问的主线来说，这一篇的落点格外贴身**：**10/3 问「一把尺子自己稳不稳」，10/4 问「尺子会不会读错动作」，10/5 问「换一张榜还灵不灵」，10/6 问「一根刻度够不够量两个方向」，10/7 问「三把尺子量出同一个数算不算量对了」，10/8 问「根本没有真值时尺子该按什么标准造」，10/9 把镜头对准 METR 那张人人引用的曲线、查它的刻度是否均匀，10/10 把镜头对准一个「安全总分」、查它能不能被读成单一属性，10/11/10/12 分别去审「一份写明了依据的推理」和「一个会传染的作弊策略」**；**今天这一篇，换了一个更基础的方向**：**当一把尺子被反复地、号称「确定性」地用来量同一件东西时，它**号称的确定性**到底成不成立？** **如果说 10/3 问的是「尺子的读数会不会自己跳动」，今天问的就是那句更狠的话**：**「这一次读数，其实根本不是『这把尺子的性质』，而是『这一次调用偶遇的那个批』的性质。」**

## 二、核心方法

**方法一点也不炫技，它的分量全在「把『重跑一遍』做成一件可归因的实验」上。** **整篇可以拆成四步**：**用一个「可能世界」模型把方差和「答案重不复现」分开 → 三家基准各自原样重跑、逐行记录 → 在三个层级上量可复现性 → 再用一组「换个部署/换个设置」的对照，把方差钉在「单次调用」上。**

**第一步：建一个「可能世界（possible-worlds）」模型——把「行级方差」和「答案能否复现」拆成两件事。** **论文对作用在 n 个条目上的语义算子建模**：**每次执行，条目 i 从它自身的输出分布 p_i 里抽出一个输出 Y_i**；**于是一次执行就是一个「可能世界」 Y=(Y_1,…,Y_n)**，**上面的计划把它映射成一个答案 Q(Y)**。**两个指标由此定义**：**①条目分歧 δ_i = Pr[Y_i≠Y'_i] = 1−Σ_o p_i(o)²**——**两次执行给出不同输出的概率**；**②答案重现值（answer reproduction） R = Pr[Q(Y)=Q(Y')]**——**两次独立执行返回同一个答案的概率**。**当条目独立变化时，Y 就是一个「元组独立「的概率关系，R 完全由 p_i 和计划形状决定，于是得到三条干净的关系**：

- **如果答案决定了每一个条目的输出**（**比如逐行 map、返回全部结果的 filter、返回全部匹配的 join**），**那么 R = Π_i(1−δ_i) ≈ e^{−n·δ̄}**——**复现概率随答案暴露的条目数**指数**衰减：当 δ̄=0.1%，一个跨 n=1,560 对的 join，复现概率只有约 0.21**。
- **对 COUNT**，**R = Σ_c Pr[C=c]²**——**正反两种变化会互相抵消，所以 R 只随计数的**离散度**下降**；**当布尔条目的方差大时，R ≈ 1/(2σ√π)**，**只通过 σ 依赖 n**。
- **对 LIMIT k**，**答案只取决于前 k 个合格条目，n 被替换成那段前缀**。
- 其它计划（**比如按均值排序**）**则用模拟穿过计划来求 R**。

**这张模型表不是装饰，它直接给出了一个反直觉的预言**：**同一批条目、同一个算子，换个计划，答案的稳定性可以差出好几个数量级**——**「全 join 和逐行输出，比 LIMIT 需要低得多的条目分歧，才能保持同样的答案稳定性」。** **论文还顺手指出了行业里那个「方差」指标本身的毛病**：**常用的「k 次执行里输出不完全相同的条目占比」，会随着 k 增大而增长**——**所以它不是一个算子的固定性质，根本没法拿来跨部署横比**。**论文为此改用「成对分歧 δ̄」（一次执行内部、跨执行都算）这个不依赖 k 的量，并在 k=5 处对齐比较。**

**第二步：三家基准，各自塞回原装 harness，原样重跑，逐行记录——关键是「不改计划、不改提示、不改打分」。** **论文把三个基准当作三条互补的证据线**：

- **SemBench**：**论文同时做了两件事**——**①直接重分析它**已发表**的结果**（**LOTUS、Palimpzest、ThalamusDB、BigQuery 四个引擎，每查询 5 次执行，Gemini 2.5 Flash**）；**②在自己的模型上重跑它的 LOTUS 实现**（**Movie 与 Medical 场景，覆盖布尔 filter、COUNT、ratio、set、AVG、分组标签、逐条打分、24 路疾病抽取、以及三条语义自连接**）。**为了不让「连接自带的随机采样级联」混进「模型方差」，论文把连接改成**在 40 条评论的种子样本上精确执行**（**1,560 个不相同评论对**）**，而不是沿用 SemBench 默认的随机采样级联。**
- **LRO-Bench**：**它定义五个「LLM 增强的关系算子」（select / match / impute / cluster / order）**，**每个算子有三种实现**（**ALL：一次调用处理整个操作数；ONE：每个元素一次调用；SEMI：混合**）。**论文在它的 14 个「算子×实现」设置上把管线原样跑一遍，无 CoT，每个部署 735 个「查询×设置」组合。**
- **UDA-Bench**：**先提取、再查询**——**从 225 篇维基百科文档里抽取属性、再用 SQL 查询**。**论文用它的 Player 数据集与 132 条查询**（**去掉了 9 条连真值都答不对的**，**剩 123 条**），**沿用它的 LOTUS 计划：每篇文档、每个属性一次抽取调用，再跑 SQL**。

**第三步：把所有执行、所有部署、所有层级都对齐成可以横比的量。** **论文通过一个 OpenAI 兼容网关调用六个开源权重部署**（**gpt-oss-120B、Llama-3.3-70B（托管 M 与 vLLM V 两套）、Qwen2.5-72B、Mistral-Small-3.1-24B、Granite-3.3-8B**），**再通过第二个网关跑两个商业模型**（**GPT-4o、Claude Sonnet 5**）。**关键的一处设计是**：**它在 harness 的模型客户端外面套了一层 wrapper，记录每次请求的哈希、每次调用的输出，并在 LOTUS 上额外记下 finish reason、token 数、**推理长度**、以及（**如果服务端给出**）**首个输出 token 的 top-5 log 概率**——**「它除了索取这些字段，不改动任何请求」**。**有了这份逐调用日志，「答案变了没变」就能被归因到「哪些算子输出变了」。** **论文最后把可复现性拆成**三个层级**来报**：**①算子输出是否逐条一致；②最终答案是否一致；③基准自己的质量分是否一致**——**并对每个部署、每套部署、每个查询都算一遍**。

**第四步：用一组「换部署、换设置」的对照，把方差的归属钉死到「单次调用」而不是「整次执行」。** **这一步是全文最见功力的地方，它把「方差从哪来」拆成四条互相独立的探针**：

- **温度控制**：**对 Movie Q3 与 Q1，把 40 个条目（一半在主执行里变过、一半没变）记录的请求重放 20 次**，**分别在 temperature 0、temperature 0+固定种子、temperature 1 下交错执行**——**以此判断温度到底有没有被应用。**
- **重复行探针**：**SemBench 的输入里有 533 条重复行**，**LOTUS 会把它们当成两条**相同**的独立请求，在**同一次执行内**发出**——**如果方差来自「贯穿一次执行的状态」，那么同一执行内的两份拷贝，应该比跨执行更常一致。**
- **单次信号探针**：**用第一次执行的**决策边际（decision margin，即首个决定输出的 token 上、两个最可能 token 的 log 概率差）**或**推理长度**，去预测哪些条目在后来的执行里会变。**
- **设置探针**：**逐项变动客户端并发数、输入顺序、推理强度（reasoning effort）、随机种子、算子实现**，**看哪一项能消掉方差。**

**这里要单独点出全文最关键的一处设计：它把「有没有答案」也当成了方差的一部分。** **LRO-Bench 的客户端对失败的查询会**重试并平均最多三次**；**论文不这么做，它**记录每一次执行、把无法解析的回复算作失败**。**这一步的直接后果，是后面那个惊人的发现**：**同一个模型（Llama-3.3-70B）在两套部署上，「至少一次执行失败」的查询比例是 59% vs 9%**——**方差在这里已经不只是「答案抖不抖」，而是「这个模型在这套部署上，到底有没有能力把答案吐成能用的格式」。**

## 三、实验结果

**结果一：重分析 SemBench 已发表的结果——五分之一的格子，质量在五轮执行之间就变了，而且「确定性计划」并不能幸免。** **论文把「一个系统在一个查询上」称为一格（cell）**。**在 101 个文本查询格子里，21 个（21%）至少有一轮执行的报告质量与别轮不同，其中 5 个相差至少 0.1，最大到 0.44**。**把图像和音频查询也算上，比例仍是 21%（224 格中的 21%）**；**在 SemBench 发表过的所有配置里，是 1023 格中的 22%**。**「每一个系统都被波及，包括把模型调用藏在服务内部的 BigQuery」。** **最能说明问题的是对照**：**ThalamusDB 会抽样、Palimpzest 的优化器会选物理算子、LOTUS 的语义连接用采样级联**——**这些引擎自身确实会引入随机**；**但论文证明引擎随机解释不了这个结果**：**在「计划是确定性的」格子里（LOTUS 非连接部分 + BigQuery），50 个有 12 个质量会变**；**在其余 51 个里，是 9 个**。**一句话**：**「已发表的格子里，大约五分之一会在执行之间改变质量，在每一个引擎上、也在引擎计划是确定性的时候。」**

| --- | --- | --- | --- | --- | --- |
| LOTUS | 49 | 24% | 6% | 0.41 | 0.010 |
| Palimpzest | 64 | 16% | 5% | 0.30 | 0.007 |
| ThalamusDB | 47 | 19% | 9% | 0.97 | 0.016 |
| BigQuery | 64 | 27% | 8% | 1.00 | 0.035 |
| **文本查询合计** | **101** | **21%** | 5% | 0.44 | 0.007 |
| **全部查询** | **224** | **21%** | 7% | 1.00 | 0.017 |

**结果二：把镜头推到「行」这一级——0.07% 到 10.2%，个别任务 24.0%，而且随执行次数还在涨。** **论文把「k 次执行里输出不完全相同的行占比」叫条目翻转率（item flip rate）**。**池化在 SemBench 的 10 个 filter/map 查询上，五轮执行的翻转率从 Mistral-24B 的 0.07%，一路到 gpt-oss-120B 的 10.2%**（**95% 置信区间 [9.55%, 10.85%]**）——**跨模型横跨两个数量级**。**而「任务」决定剩下的一切**：**同一个 gpt-oss-120B，在布尔 filter 上是 3.4%、在两路标签上 3.3%、在 1–5 分打分上**17.5%**、在 24 路疾病抽取上**24.0%**。**同一个 Llama-70B（M），布尔输出只翻 0.19%，抽取却翻 7.8%**——**「一个在 filter 上看起来确定性的模型，到了 map 上可以变得相当不稳」。** **商业模型也不能幸免**：**GPT-4o 翻 7.5%，Claude Sonnet 5 翻 4.1%**，**都落在开源部署的区间之内，且都以 1–5 分打分翻得最多**。**还有一条更反直觉的**：**这个比率不是部署的固定性质**——**gpt-oss-120B 从两轮执行的 5.2%，涨到五轮的 10.2%，再涨到十轮的 13.0%，一直没有收敛**（**打分任务从 8.8% 涨到 22.3%**）——**「所以只看几次执行，只能揭示可能变化的行里的一部分」。** **论文特意点出：「输出空间的大小」本身解释不了这个**——**UDA-Bench 的抽取是开放输出空间，绝大多数取值却相当稳定；而变化最多的是那些「文档里提到了好几个候选」的属性**（**比如球队的所有者、城市的人口**）。**一个 100 条合成商品评论的对照更直接**：**复制一个城市从不改变；一个六路情感打分在 11% 的评论上改变；一段自由文本摘要则在 82% 上改变。**

| --- | --- | --- | --- | --- |
| 布尔 filter | 3.4% | 0.19% | 0.00% | 2.22% |
| 两路标签 | 3.3% | — | 0.83% | 0.00% |
| 1–5 分打分 | 17.5% | — | 9.04% | 4.65% |
| 24 路抽取 | **24.0%** | 7.8% | — | — |

**结果三：真正决定「答案稳不稳」的不是模型，而是计划——几个百分点的行变化，就能掀翻大多数答案。** **论文把「行变化」一路推到「答案变化」**：**「一条变化的行，只有在它改变了答案时才有意义」**。**SemBench 的连接给出了最干净的一击**：**Q7 返回 1,560 对评论里所有的「相反情感对」，因此**任何一条判定变化都会改变答案**——**只有 Mistral-24B（它一条都不变）能复现它**；**Qwen-72B 与 Llama-70B（V）只变了 0.3% 和 0.2% 的判定，却只在 0.10 和 0.20 的执行对里复现**——**「与独立性预测的 0.16 和 0.15 非常接近」。** **在 UDA-Bench 上，放大效应最戏剧化**：**Llama-70B（M）只改变了 4.0% 的抽取值，结果表却在 123 条查询里有 83 条（67%）在重跑之间不同**；**gpt-oss-120B 是 7.5% 的取值、68% 的答案**——**「大多数查询是读一张表里每篇文档的同一个属性，一百个取值里变一个就够了」。** **而质量指标会把这些全部藏起来**：**UDA-Bench 上质量只在 78 条查询上变化，且幅度很小（平均幅度 0.031，最大 0.17）**——**「一个用户重跑查询，看到不同**结果表**的概率，远高于看到不同**分数**的概率」。** **论文据此把可复现性拆成**三个层级**来报，并指出每一层都会瞒住下一层**：**平均到各部署，SemBench 有 32% 的查询算子输出全一致，48% 答案全一致，52% 质量全一致；LRO-Bench 是 44%/59%/71%；UDA-Bench 只有**2%/19%/33%**。** **「算子输出与答案之间的落差，就是计划吸收掉的东西；答案与质量之间的落差，就是指标看不见的东西。」** **论文还给出一句可直接落地的规范**：**「一个报告可复现性的基准，必须声明它说的是哪一层。」**

**结果四：它把 LRO-Bench 那份「实现建议」直接拿去重跑——28 项测试里，16 项根本没被现有的执行定论。** **LRO-Bench 会为每种算子、每种操作数推荐一种实现**（**比如 filter 按行时 ONE 优于 ALL**）。**论文在四个部署上测了其中 9 条建议**，**用自助区间比较两种实现的平均质量，并逐执行检查**。**结果**：**28 项测试里，12 项在每一轮执行里都成立，且没有一项被**反向**推翻，但有 16 项的自助区间**包含零**（即没定论）**；**在 6 项里，单轮执行之间连「哪种实现更好」都互相矛盾**——**「所以一轮执行既可以支持这个结论，也可以支持那个结论」。** **只有一条建议**——「filter 在列和表上，ALL 优于 ONE」——**在每一个部署上都成立**。**论文很克制地标注**：**「我们的模型与 LRO-Bench 用的不同，所以这测的是建议的**稳定性**，不是已发表的数字。」** **而更上游的一击是**：**gpt-oss-120B 在 726 条「被作答」的查询里，有 413 条（57%）的答案在重跑之间不同**——**「每一个算子都被波及：select 38%、match 59%、impute 69%、cluster 62%、order 62%、多算子管线 37%」。**

**结果五：方差不是「隐藏温度在采样」，而是「这次调用」的性质——它专挑「接近平局」的行下手。** **论文做了四组探针，条条指向同一个结论**：

- **温度确实被应用了，但还是没消掉方差**：**在条目层面，temperature 0 下两次执行分歧 2.5%，temperature 1 下 7.5%**；**在「主执行里变过的行」上，这个差距是 12.1% vs 41.1%**——**「所以 temperature 0 是被应用的、它降低了方差，但没有消掉它」。** **固定种子也没有一致效果。**
- **变化的行，是「有争议的行」**：**SemBench 上，77% 的变化行是「其它部署的多数输出都不同意」的争议行，而稳定行只有 34%**；**gpt-oss-120B 在「所有其它部署都一致的条目」上只变 3.2%，在「三个部署都反对其余」的条目上变 37.5%**——**方差集中在「模型们本来就各执一词」的模糊条目上。**
- **方差属于「这次调用」，不属于「这次执行」**：**SemBench 的 533 条重复行（LOTUS 在同一次执行内当成两条相同请求发出）**，**在 gpt-oss-120B 上，同一执行内的两份拷贝分歧 6.0%，跨执行的分歧 6.1%**——**「如果方差来自贯穿一次执行的状态，同执行内应该更常一致；它没有」。** **更狠的是**：**某条 Q9 评论在**同一次执行内**拿到了两个不同的分数（10 次执行里 6 次如此）**；**533 条重复输入里有 91 条，在 gpt-oss-120B 的至少一次执行内拿到了两个不同输出**——**「所以一条答案，可以建立在同一个输入的、互相矛盾的两个输出之上」。**
- **一次执行就能预告哪些行会变**：**用第一次执行的决策边际，就能把「后来会变的行」和「不会变的行」分开**——**Granite-8B 的 AUC 是 0.93**（**Llama-70B（V）、Qwen-72B 甚至到 1.00，尽管变化行只有 17 和 5 个**）。**gpt-oss-120B 的栈不返回 log 概率，但**推理长度**起到了同样的作用**（**AUC 0.84，1,057 个变化行**）。**拟合出一个噪声尺度**：**Granite-8B 的 σ=0.28 nats**——**「边际低于 1 nat 的条目占 Granite-8B 的 7.8%，却占了它 78% 的变化」**。**一句话**：**「方差作用于接近平局的条目，这正是它为什么集中在争议条目上、也是为什么投票消不掉它。」**

**结果六：连「换个部署」都能改写答案、改写方差、甚至改写「有没有答案」。** **论文用同一份权重、同一个模型名、同一个提示，在托管服务（M）与 vLLM 部署（V）上跑 Llama-3.3-70B**：**两者在 4,736 个 Movie 条目里，有 83 个（1.8%）多数输出不同**——**而每一套部署**内部**只有 0.7% 的条目会变**。**「每一套部署在 Movie 上几乎都是确定性的，但两套部署是**确定性地不同**」**：**Movie Q3 在一套上永远得 0.43，在另一套上永远得 0.36**。**两套部署的**方差**也不同**：**24 路抽取上，M 翻 7.8%，V 只翻 0.7%**。**最极端的是 LRO-Bench**：**「部署决定了到底有没有答案」**——**至少有一次执行失败的查询，M 上是 437/735（59%），V 上只有 64（9%）**；**而 M 的失败回复里，39% 在 JSON 前带文字、2% 包在工具调用信封里、42% 形状不对、17% 根本没有 JSON**——**「一个宽容的解析器最多也只能救回前两组，所以 M 仍会失败得多得多」。** **而且失败是可复现的**：**437 条失败查询里，只有 43 条在另一次执行里成功。** **部署还会随时间漂移**：**M 在主执行里对某 736 个条目每次输出都相同，但把主执行和后来一轮 campaign 对比，跨 campaign 的执行对在 1.9% 的条目上分歧**（**Granite-8B 所在的 V 则没有这种漂移**）。**与此同时，论文测过的**所有客户端设置**——并发数、输入顺序、推理强度、随机种子、算子实现——**没有一个能消掉方差**：**6 组对比里，「分歧变化量」的 95% 自助区间全部包含零。** **「一个请求一次」并不能让 Granite-8B 变确定**（**Q3 上分歧仍有 1.65%，与「一个会批处理所有租户请求的服务器」一致**）。

**结果七：补救有效但有限——投票消不掉方差，真正让答案可复现的是「把算子输出记下来」。** **论文在 gpt-oss-120B 的十次记录执行上**重放（不新增模型调用）**各种补救**：

- **投票**：**三票消掉 36% 的成对分歧，五票消掉 48%**——**但两者都**不能**让聚合、排序或 Medical 的答案变得可复现（没有两组合并执行返回同一个答案）**。**原因在分布里**：**48% 的变化行，它们的少数输出在十次里出现了至少三次，所以三票仍然会把它选出来**；**而投票对准确率的改变最多只有 1.8 个百分点**——**「因为方差只是误差里较小的那一部分」**：**多数输出在 17.9% 到 30.7% 的标注条目上本就是错的，而变化只占至多 9.9%。**
- **选择性投票**：**既然推理长度能预告变化，引擎可以只对「被标记的条目」重启**——**对最长推理的 20% 条目重启，就能拿到整轮投票 64% 的收益，代价是每条目 1.4 次调用；30% 拿到 80%，代价 1.6**；**而随机重启 20% 只有 29%。**
- **校准级联**：**论文重放了一个 90% 召回、95% 置信的代理级联**——**「统计保证」在有方差的 oracle 上**存活**了，但它**返回哪些行**却取决于哪一轮 oracle 执行给样本打了标签**：**Medical Q1 上，同一个 400 行样本被两轮不同 oracle 执行标注，只有 24% 的情况返回相同的行。**
- **记录输出**：**唯一真正让答案可复现的补救，是把「这条答案来自哪些算子输出」记下来**——**「它还很便宜：一个存储输出约 39 字节，gpt-oss-120B 跑一遍十个 SemBench filter/map，产生 348 KB 的输出。」**

## 四、技术启示与发展方向

**第一，给「确定性」这个词祛魅：temperature 0 是一条**关于解码策略**的假设，不是一条**关于答案**的保证。** **论文最锋利的一句是它的**因果归属**：**方差属于**每一次调用**，而不属于**整次执行**（**同执行内的两份相同请求，跨执行同样会分歧**）；**它也不是「隐藏温度在采样」**（**temperature 0 确实被应用了，只是没消掉方差**）。**它的真正来源，是服务器在**批组成**层面的浮动归约顺序**——**也就是说，一个请求的 logits 取决于「谁和它共享了那个批」**。**这件事对任何把 LLM 当作「可复用材料」的系统都是一记提醒**：**当你把模型输出物化成列、当成优化器校准的标签、存进缓存时，你存下的其实是**一次抽样**，而不是**一个真值**。

**第二，一个可以直接搬去任何「LLM 当算子」系统的诊断顺序：先量**行级**分歧，再用**计划形状**推**答案级**复现。** **论文把这条链讲得很清楚**：**行级分歧 δ 是**地基**；答案能暴露多少行（n）**由计划决定**；**R ≈ e^{−n·δ̄}**。**于是可操作的三步自查是**：**①在你的算子输出上量成对分歧 δ̄（不要用那个会随 k 增长的「翻转率」）；②数一数一条答案究竟暴露了多少行；③套进 e^{−n·δ̄}**，**就知道你的答案该不该被信任**。**论文还指出那条最容易被忽视的规范**：**「不要把几次执行里**最好的一次**报出来，也不要把失败执行**重试掉**」**——**因为「最好的那次」正是方差给你的一件礼物，而「被重试掉的失败」恰恰是**答案的一部分**。

**第三，一句可以直接改写「基准怎么写」的立场：把**质量**、**答案复现**、**失败率**并排报出来。** **论文给出的「基准设计者清单」几乎是通用的**：**①报每查询质量**连同它的离散度**，执行次数按观测到的方差**选**（SemBench 的五次，对 112 个文本比较里的 7 个来说不够）；**②在质量旁边报「答案复现值」；③在**指定**的执行次数上报翻转率，或报成对分歧；④不报最好一次，把失败执行及其**比率**当作**结果**报出来；⑤记录**逐条目输出**，好让别人免去重新调模型就能归因方差、重放补救；⑥报出每个开源权重模型的**部署**；⑦一条**方法建议**，只有在**跨执行**成立时才能给出**。** **第 ⑦ 条正是 LRO-Bench 那 16/28 的直接教训。**

**第四，一组给「引擎构建者」的设计规则：把「一条语义列」当成分布里的**一个样本**来存。** **论文的建议很具体**：**①存语义列时，连同它的**决策边际**或**推理长度**一起存**——**想要「每个输入一个答案」的引擎，必须在**一次执行内**去重调用，而不只是跨执行去重**；**②用「条目分歧 × 计划形状」估计答案稳定性**——**暴露 n 个条目的答案，复现概率约 e^{−n·δ̄}**，**所以全 join 和逐行输出，需要远比 LIMIT 更低的条目分歧**；**③「拿一轮 oracle 执行去校准」的优化器，会**继承那次执行的方差**——**保证可能存活，但计划不会**，所以要**把校准标签连计划一起记下来**；**④选算子实现时，看的是成本和对回复格式的稳健性，不是稳定性**（**因为根本没有一种实现对所有算子都最稳**）；**⑤要复现一条答案，就复用它**记录下来的算子输出**。**

**第五，边界划得诚实，而且划在了显眼处。** **论文主动列出几处局限**：**跑不了 Gemini 2.5 Flash，所以 RQ2–RQ5 依托六个开源权重部署**；**没有任何可及的模型能「带推理/不带推理」地都在 temperature 0 下跑，所以无法把「推理」和「模型」分开**；**逐条目日志需要在引擎的模型客户端里挂钩子，论文只为 LOTUS 和 LRO-Bench 的客户端做了**；**逐条目日志只有返回 log 概率的部署才有**；**覆盖范围仅限文本与表格数据**；**连接用的是 40 条评论的样本**；**「部署效应」只建立在一个模型、两套部署这一对上**。**最值得记的一条是它对**次数**的坦白**：**「五次执行，限定了我们能检测到的最小翻转率，也让答案复现值只有 0.1 的粒度；而翻转率仍在增长——Granite-8B 在五个 Movie 查询上，五次执行翻 3.1%，到四十次执行翻 5.2%。」** **这句话本身，就是对任何「跑几次就够了」的基准的一记反问。**

**第六，一组指向未来的开放问题：当「确定性」被逐层拆穿后，「可复现」这三个字该落到哪一层？** **论文给出的答案其实只有一句话**：**「要复现一条答案，就复用它记录下来的算子输出。」** **这句话把「可复现」从一个**关于模型的**性质，改写成了一个**关于记录的**性质**。** **对本系列主线而言，这一篇把 10/3 到 10/11 的追问**合流**到了最底层**：**10/3 问「尺子自己稳不稳」，今天给出的是一个更基础的答案**——**「稳」不是尺子（模型）的属性，而是「你记没记住这次读数」的属性**；**10/9 问「一把现成尺子的刻度匀不匀」，今天则证明**连「这次读数」都不属于尺子，而属于「这一次调用碰巧待的那个批」**。** **而它与 10/5「换一张榜还灵不灵」形成了一组对称**：**10/5 问的是「换了个榜单，结论还成不成立」；今天问的是「同一个榜单，再跑一次，结论还成不成立」**——**后者比前者更基础，也更常被跳过。**

## 五、总结

**这篇论文做了一件很朴素却很有分量的事：把「同一个查询重跑一遍会得到同一个答案」这句被整个语义查询领域默认接受的话，重新当成一个待核验的断言，然后拿着 121.9 万次模型调用去跑了一遍。** **表面上，它给出的是一组很干净的对照**：**temperature 0 下，五轮执行之间 0.07%–10.2% 的行会改变输出（个别任务 24.0%），SemBench 已发表结果里 21% 的文本格子质量会变，而**几个百分点**的抽取值变动，经过计划一放大，就能让 UDA-Bench 上约**三分之二**的答案变样**；**LRO-Bench 的 28 项实现建议里，16 项撑不过重跑**。**换个角度，真正值得记下来的不是这些数字，而是那个被量出来的**归属**：**方差不属于「这次执行」，也不属于「隐藏温度」，而属于**每一次调用**——**它专挑「接近平局」的条目下手（边际低于 1 nat 的条目只占 7.8%，却占了 78% 的变化）**，**所以投票消不掉它**；**它还会因为「换一套部署」而整体偏移（同一份权重，Movie Q3 在一套上永远 0.43、在另一套上永远 0.36）**。**再往里挖一层，决定一切的还是那个老道理**：**一条答案的稳定性，既不由模型单独决定，也不由计划单独决定，而由**「一条答案暴露了多少行」乘以「每一行有多接近平局」**共同决定**；**而这两样东西，恰恰是「跑一次取个数」这个默认动作最看不见的。**

**论文留下的最核心一击，是「temperature 0 并不能让一次语义查询变得可复现」**。 **它把一个人人都在做、却很少被系统检验的动作摆上台面**：**「我们跑一遍，拿到一个数，就把它写进表格、当成这个系统的性质。」** **而它最有价值的一手，不是简单说「模型有随机性」，而是拿出**一整套可复用的审计工具**——**可能世界模型（把行级方差和答案复现拆开）、成对分歧（不依赖执行次数的横比量）、三层级可复现性报告、以及「换部署/换设置」的四条因果探针**——**并且诚实地标出哪几问能查、哪几问得让给未来。** **对本系列的主线来说，这一篇把「测量有效性」的追问，从「审一把尺子的刻度匀不匀」（10/9）、「一个总分够不够格被读成一个属性」（10/10）、「一份写明依据的推理可不可信」（10/11），推进到了最底层的一步**：**把「这把尺子**号称**是确定的」这句话拿上审计台，去看这种「确定的读数」到底属于谁。** **如果说前面几篇问的是「一个读数**读得对不对**」，今天问的是另一个方向、也更基础的一件事**：**当一把尺子被反复量同一件东西时，你拿到的那两次相同读数，到底是这把尺子**稳定**，还是你**恰好**在两次里碰上了同一个批**？** **它给出的忠告，几乎可以当作任何一次「LLM 当算子」的通用注脚**：**「别急着把一次执行当成这个系统的性质——先量一量它有多少行会在重跑时翻脸、这些行经过你的计划会被放大成多少；然后，把你据以生成答案的那些算子输出**记下来**。」**
